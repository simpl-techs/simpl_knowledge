# simpl_api integration guide

> **Maintained by**: the `simpl_api` repo, auto-synced to simpl_knowledge.
> **Source of truth**: `simpl-techs/simpl_api/.agent/SKILL.md`

Payment frequency is separate from cost allocation: `payment_frequency` is `one_time`, `monthly`, `annual`, or null (unknown). Vendor assignments and manual expense batches persist it; classification carries it to the ledger and preserves manual decisions. It does not generate future transactions or require an end date. Existing decisions remain null; `covers_months` is never interpreted as cadence. Apply the additive `roi_payment_frequency` migration before deploying the updated Core/API.

## What this service is

`simpl_api` is the FastAPI backend for the simpl sales intelligence platform. It exposes app/admin API routes, webhook handlers, guided/autopilot endpoints, prompt/template services, background jobs, and agent-facing backend workflows.

## Installation

```bash
conda env create -f environment.yml
conda activate simpl_api
poetry install
cp .env.example .env
```

This repo is normally deployed as a service, not installed as a dependency by other repos.

## Basic usage

```bash
conda activate simpl_api
poetry run uvicorn simpl_api.main:app --reload
```

When adding API behavior, place HTTP route code under `src/simpl_api/api`, reusable business logic in `simpl_core` or `src/simpl_api/services`, and schemas under `src/simpl_api/schemas`.

## Rules and conventions

- Keep FastAPI route handlers thin. Move reusable domain behavior to `simpl_core` or a service module.
- Use Pydantic schemas for request/response contracts.
- Keep environment variables documented in `README.md` and `.env.example` when adding new config.
- Use existing agent/service patterns before introducing a new orchestration style.
- Emails a user's SimpL agent sends go through the `email` channel plugin and `services/channels/agent_email.py`: a plain email in the agent's words, one link into SimpL, signed as the user's own agent persona. Pass `brain.notify_user` a `body` (and optionally `subject`, `route`); don't build HTML.
- A seller's outbound email signature is `GET`/`PUT /api/v1/app/email-signature` (`html`, `plain`). HTML is sanitized with `simpl_core.services.email.signature` and stored on `sales.user.email_signature_html`. Apply `migrations/20260907_user_email_signature.sql` before this route is deployed. The journey email flow appends it at send time; this route does not send mail.
- A seller's active hours, when the extension may send, are `outreach_prefs.active_hours` = `{"start": "HH:MM", "stop": "HH:MM", "timezone": "<IANA name>"}` (start inclusive, stop exclusive, start before stop). A missing field takes 07:00 / 19:00 / UTC, and an unset or invalid window runs on 07:00-19:00 UTC. `sales.resolve_active_hours(prefs jsonb[, at timestamptz])` resolves it: the extension task RPC gates on it, and `GET`/`PATCH /api/v1/app/preferences` return its answer as `active_hours_effective` (`start`, `stop`, `timezone`, `source` = `configured` | `unset` | `invalid`, `is_open_now`). `PATCH` merges `active_hours` one level deep, `null` resets it, and a value the resolver calls invalid, or a zone not spelled exactly as in IANA, is refused with 422. Read the window through the resolver (`services/active_hours.py`) instead of re-parsing the JSON. Review-answer follow-ups (`review_response_service._next_business_morning`) schedule at the start of the seller's window, 09:00 Europe/Rome without one, like simpl_core's retry triggers (simpl_core >= 0.8.2).
- Authenticate product routes with `auth.get_current_user`, which also refuses SimpL Challenge entrants; scope them with `simpl_api.guards`, whose `resolve_user_context` repeats that refusal against the database. Both are single places, so a new endpoint written against the ordinary dependencies inherits them. Do not reimplement either check per endpoint.
- Approval routes (journey-log `set-pending`, managed approve, Agent API draft approve and `bulk-approve`) and invite execution return the status the database settled on. simpl_core's dispatch authority rule can send an approved row back to `PENDING_APPROVAL` (`payload.authority.block_reason`) or cancel it, so callers must not assume `PENDING`; `bulk-approve` lists such rows under `withheld`, and invite execution answers 409.
- Regenerating a pending draft is asynchronous (simpl_core `request_regenerate`; the outreach worker rewrites it). Seller: `POST /api/v1/app/journey-log/{id}/regenerate` `{additional_prompt?}` (other legacy fields are ignored) answers 202 `{kind: "queued", journey_log_id, request_id, trigger_id, requested_at, late_after_seconds: 900, regenerate_pending}`, where `regenerate_pending` is the draft's `payload.regenerate_pending` marker; only message drafts (`send_message`, `linkedin_connect`, `invite_call`) awaiting approval qualify (409 `invalid_transition`), 404 when the draft is not the caller's. Poll `GET /api/v1/app/journey-log/regenerate-jobs/{trigger_id}?request_id=` for `{status: queued|running|rewritten|replaced|review_request|no_result|failed|cancelled, trigger_id, request_id, journey_log_id, scope, requested_at, late, reason, reasoning, version_index, new_journey_log_id, new_journey_log_status}` (404 when not the caller's job). `POST /api/v1/app/journey-log/{id}/regenerate/cancel` answers `{cancelled, request_id, trigger_id}` once the regenerate failed or is late (15 minutes), else 409 `regenerate_not_cancellable`. Managed operators have the same three at `/api/v1/admin/managed/actions/{id}/regenerate`, `/api/v1/admin/managed/actions/regenerate-jobs/{trigger_id}` and `/{id}/regenerate/cancel`, acting for the draft's owner (`requested_by: admin:<id>`). The Agent API's `POST /api/agent/v1/drafts/{id}/regenerate` answers 202 `{journey_log_id, status: "queued", request_id, trigger_id, agent_instructions}` and `GET /api/agent/v1/drafts/regenerate-jobs/{trigger_id}` the same job shape. An approved Sales Domain `writer_regenerate` queues a forced rewrite per draft through simpl_core's command (`queued` / `skipped` / `failed` per row).
- While a regenerate is queued or running the draft is locked: every journey-log write (seller and Managed approve, edit, reject, reschedule, version switch, regenerate, review answers, invite execution, manual email/invite confirmation, Agent API approve/reject/update) answers 409 `{"detail": {"code": "regenerate_in_progress", "message": "..."}}` (the Agent API adds `error` and `agent_instructions`). Agent API `bulk-approve`/`bulk-reject` leave such drafts alone and list them under `regenerating`. A regenerate that failed unlocks the draft and keeps its marker (`state: failed`) for the card.
- Outreach previews are retired: `POST /api/v1/outreach/preview`, the `dry_run`/`preview` modes of `POST /api/v1/outreach/simulate` (`mode` is now required, `persist` or `traced`) and the customer chat's `build_outreach_preview` tool. simpl_api runs no outreach walk and no longer depends on simpl-outreach. `POST /api/v1/outreach/simulate` and `POST /api/v1/outreach/simulate-inbound` write a fake inbound message and its `message_received` trigger on any `ulc_id`, so they take `require_admin` (`sales.user.is_admin`: owner, admin, staff) and a customer's token gets 403, even on its own connection. `POST /api/v1/outreach/commit-preview` is removed (404); its only caller, the dashboard's outreach workbench, went in simpl_dashboard #99.
- Who takes a team's meetings (simpl_core `TeamHandoffService`, `services/team_handoff.py`): each member's own hand-off (`sales.user.handoff_to_user_id`) and the team rules (`sales.responsibility.owner_user_id`), written as the team table. `GET /api/v1/app/team/handoff` (any member) returns `members[]` (`handoff_to_user_id`, resolved `taker_user_id`, `needs_colleague`), `rules[]`, `can_manage` and the viewer's `colleague_ids`. `PUT /members/{user_id}` `{handoff_to_user_id}` sets one's own (managers: anyone's); `POST /rules`, `PUT /rules/{key}` `{description, owner_user_id}` and `DELETE /rules/{key}` are for managers (owner, billing_admin, manager). Staff have the same at `/api/v1/admin/customers/{id}/handoff`. Refusals carry `detail: {code, message}`: `identity_needs_handoff` / `invalid_handoff` / `invalid_policy` (422), `not_found` (404). Every path that changes a member's role, activity or customer (`PATCH /app/team/role`, admin user PATCH, assign/remove, disable/enable, permanent delete) ends with `sync_team_handoff`.
- Role `sales_identity` (migration `20261010b_sales_identity_role.sql`): a sending account that never takes a meeting. Invited with `handoff_to_user_id` (admin `invite-user`, customer `invites`/`invites/batch`) or, in a customer setup, `handoff_to_email` naming another invitee; flow `invite_identity`. Without one it chooses on the onboarding `handoff` step: `GET`/`PATCH /api/v1/onboarding/session/{id}/handoff` (team members who take meetings, or the setup's other invitees). A role change to `sales_identity` needs `handoff_to_user_id` unless the member already hands off. Customer-side invites are open to owner, billing_admin and manager, and to icp_manager on pay per call.
- Inbound to onboarding: `POST /api/v1/admin/customer-setups/from-session/{session_id}` `{billing_options, name?, notify=true}` turns a request-access session into the owner's invited onboarding on the same login and session (setup + accepted owner invite, back at the first step with their answers kept). Returns `setup_id`, `invite_id`, `onboarding_url`, and `email_error` / `billing_error` when one of those did not go through. 409 for a session that is not an inbound request, already has a setup, belongs to a `sales.user`, or whose address has an open invite.
- `GET /api/v1/onboarding/session/{session_id}/booked-call` -> `{booked, start, end}`: the request-access call, read from Nicolò's calendar (the snapshot also carries it as `context.booked_call`). `GET /api/v1/admin/onboarding/followups/preview` -> `{enabled, in_send_window, notes}`: the follow-up emails that would go now (sent only with `ONBOARDING_FOLLOWUPS_ENABLED=true`).
- Onboarding connects the mailbox and calendar on the accounts page (`/api/v1/onboarding/session/{id}/connections[/{toolkit}]`: `GET`, `POST {callbackUrl}` -> `redirectUrl`, `PUT {connectedAccountId}`; gmail, outlook, googlecalendar). The person has no `sales.user` row yet, so the account is parked in the session (simpl_core `onboarding_choices`) and the finalize (simpl_flow) attaches it with the hand-off.
- Onboarding sessions by login: `GET /api/v1/admin/onboarding/by-user/{user_id}` (`require_admin`) returns the full session envelopes (`AdminSessionSummary`, as `GET /admin/onboarding/sessions/{id}`) the login owns, most recently updated first, `[]` when none. The dashboard's support inbox uses it for people who write while still onboarding (no `sales.user` row yet). `/admin/onboarding/by-customer/{customer_id}` is the same through `onboarding.provision_link`.
- A colleague's hand-off is passed on from one of its cards: `GET /api/v1/app/journey-log/{id}/handoff-redirect` returns the objective behind the card (`objective_id`, `responsibility_key`, `state`) and the colleagues it can go to (`targets[]`: `user_id`, `full_name`, `responsibility_key`, `description`). `POST` with `{to_user_id, reason?}` moves it (simpl_core `AccountCoordinationService.redirect`). The targets come from the team table, not from the caller. The old hand-off closes and its queued cards are cancelled, and the new owner is woken. A card that isn't the caller's, or has no `coordination_objective_id`, gets 404. A colleague the table does not allow gets 403, naming the allowed ones. A closed hand-off, or an open one already on the target's responsibility, gets 409. Repeating the same move replays it (`replayed: true`). Managed operators have the same pair at `/api/v1/admin/managed/actions/{id}/handoff-redirect`: the managed-scope check resolves the card's owner, the move is made as that owner, and the operator is recorded in `sales.audit_log` (`managed.action.handoff_redirect`).
- "Propose other times" on an invite card: `POST /api/v1/app/journey-log/{id}/propose-times` with `{times: [{start, timezone}] (1-3), note?}` (`start` is ISO 8601 with its UTC offset).
- The app chat's outbox (`src/simpl_api/api/v1/app/conversation_outbox.py`, `services/conversation_outbox.py`): a seller writes to a lead on LinkedIn or by email from the Home. `GET /api/v1/app/conversations/outbox?ulc_id=` (the thread's connection; its owner or a teammate of the same customer) returns `senders`, every connection and channel the viewer may write from: their own connection to the lead, and a colleague's when they share a hand-off on that lead (an `account_coordination_objective` not cancelled, the viewer one participant, the connection the other's role connection), each `linkedin_message` and `email`, with `available`/`reason` (`not_connected`: no `sales.connection`; `no_mailbox`: no active Gmail/Outlook; `no_email_address`: `LeadContactRepository.find_best_contact` for the owner; `no_company`; or the dispatch authority rule's reason, asked of `sales_outreach.evaluate_dispatch_authority` before offering, e.g. `account_handed_off`) and one `is_default` (the thread's LinkedIn when it can send); and `messages`, the last 30 days of chat messages to the lead from any of its connections (`ulc_id, channel, sender_user_id, sender_name, message, subject, status, created_at, scheduled_at, executed_at` (once settled), `error`, `review_reason`, `can_withdraw`, `blockers` from `sales.user_dispatch_blockers` for a queued LinkedIn one). `POST /api/v1/app/conversations/outbox` `{ulc_id, channel, message, subject?}` queues a `send_message` journey_log on that connection (`message_type: response`, `payload.created_by = run_id_trigger = seller_chat`, `written_by`; email adds `recipient_email` and `subject`, the first line when none), linked to the hand-off objective for a colleague's connection, inserted `PENDING_APPROVAL` and approved by the writer through `JourneyLogRepository.set_pending_with_version` in one transaction so the authority trigger judges it like an approved draft; 201 with the settled status, 404 when the writer may not use the connection, 422 `{code: unavailable, reason}`. It goes out from the connection's owner: LinkedIn through their extension (three minutes after `scheduled_at`), email from their mailbox via simpl_flow's `gcp_journey_email_flow`, which the route starts at once (best effort; the deployment runs one flow at a time). The run is the connection's active one, else the standard journey's (`accb2e01-…`), else its latest. `POST /api/v1/app/conversations/outbox/{journey_log_id}/cancel` withdraws a queued one (writer or connection owner, row lock, `payload.cancellation.reason = withdrawn_by_writer`), 409 once a sender has it. `migrations/20261008c_outbox_read_grants.sql` grants django_simpl_user EXECUTE on the two functions; without it both reads fall back (savepoints) and the trigger alone judges the row.
  - **Checks:** the times are held to simpl_core's `proposed_times_problems` (future, offset matching the IANA zone, no duplicates); otherwise 422 `{code: invalid_times, problems}`. A card that isn't the caller's gets 404. A card that isn't an `invite_call` gets 409 `not_an_invite`. A card not awaiting approval gets 409 `not_pending`. A closed hand-off gets 409 `handoff_closed`.
  - **Effect:** the card is cancelled (`payload.cancellation.reason = seller_proposed_other_times`, with the times and the note), in one transaction with one of two effects:
    - `route: own_conversation`, for a card with no hand-off: a `human_review_resolved` re-entry on the card's connection, with `selected_option_id = propose_other_times`, `proposed_times` and `note`. simpl-outreach replies offering exactly those times.
    - `route: handoff_source`, for a card linked to an open objective: the owner's `need_information` with `proposed_times`, which wakes the colleague who started the hand-off, since they are the one talking to the lead.
  - **Replays and events:** repeating the call on a card already cancelled this way replays it (`replayed: true`) and writes nothing. A `user.action.proposed_other_times` outreach event is logged.
  - **Managed:** operators have the same route at `/api/v1/admin/managed/actions/{id}/propose-times`. It acts as the card's owner, records the operator in `cancellation.cancelled_by` (`admin:<id>`), and writes `sales.audit_log` (`managed.action.propose_times`).

- The funnel's ROI block is `POST /api/v1/app/reports/value` and `POST .../value/seat-request`. It is a staff beta: only SimpL staff (`is_admin`) get it, 403 for everyone else, and the response says `beta: true`. Setting `ROI_RELEASED_TO_CUSTOMERS=true` (also `1`/`yes`/`on`) in the API environment releases it to the customer's owners, billing admins and ICP managers; unset or any other value keeps it staff-only. The cost follows the model Stripe bills (a pay-per-call account line means pay per call; the database model only when Stripe cannot say). Staff can send `simulate_pay_per_call: true` to price a seat customer as if it paid per call (`simulated: true`, `viewer.can_simulate`); anyone else gets 403. The seat request is how ICP managers ask owners and billing admins for accounts through the governed in-app notification. `rolling` (7, 30, 90) is the window of the funnel metrics beside the block and `offset` (0-104) moves it back that many windows; the response's `period` is that window itself, not a pace: its leads and meetings, the new customers its meetings bring at the close rate, their value, what SimpL cost in it (seats: the subscription for its days at today's price; pay per call: the calls charged in it) and `roi`, with `has_earlier` to stop going back at the first lead, or at the window pay per call began in (`cost_counted_from` set, `roi` empty: the seats paid before are unknown). The monthly figures and the forecast are that window's pace. All arithmetic lives in `services/customer_value/model.py`. `sales.icp.deal_size` means the yearly value of one new customer won from that ICP, in the customer's billing currency; it is set with `PATCH /api/v1/app/icps/{icp_id}/deal-size`, and the ROI prefers it over the median of `sales.deal`. `GET /api/v1/app/reports/value/expected` is open to every user of a customer, released or not: only `meeting_to_deal`, `deal_value` (null until set or until 3 deals of their own), `cohort`, `icps` and `can_set_deal_value` (owner, billing admin, ICP manager, manager), for the simpl_sales Home's revenue estimate; no cost, ROI or seats. The close rate counts a deal only as one of the window's meetings sold on or after it (`company_funnel_facts.first_closed_at`), and its benchmark pools SimpL's own account (`PeerCustomer.internal`, Raff 2026-10-08) beside the paying peers; SimpL never enters a cohort, its size, the lead rates or the deal median.
- Billing runs without rollout switches: the pay-per-call cycle (record, three-day contest window, Stripe posting, invoices), the hourly Growth price transitions and the call-evidence moves into Negotiation always run. What a customer pays is decided per customer, by its billing model and its Stripe subscription. An account that must pay nothing (SimpL's own) is a pay-per-call customer in billing mode `comp`, a 100% coupon on its subscription: its calls are recorded, posted and invoiced like anyone's, at zero. The call-evidence job applies the evidence of the last 30 days it has not applied yet, at most 500 per run.
- Pay per call (`sales.customer_subscription.billing_model = 'pay_per_call'`): accounts are free and each company is charged once, when its first call that took place is attributable to SimpL (`sales_view.billable_calls`: the company moved into Negotiation, or into Closed, backed by evidence that the call took place (Recall recording, calendar acceptance, the outreach agent reading the post-call conversation, the seller's or an admin's confirmation); the customer claimed it in SimpL and wrote to it before the meeting), from `billing_model_since` on, at its ICP's `sales.icp.call_price_cents`: the EUR 70 base rate (`DEFAULT_CALL_PRICE_CENTS`, `services/call_pricing.py`; a stored price is never repriced), or a price the customer accepted in an order (an onboarding order prices the owner's ICPs from the pool calculator, see below); calls with no ICP use `default_call_price_cents`, EUR 70 when unset. For a customer whose adopted order is on terms 2.x (2.0.0 or the current 2.1.0), the order applied when the call was held decides that v2 rules apply, but the price comes from the order applied when the customer first worked the company (its claim: the customer's first `user_lead_connection` to it; their first order when the claim came earlier; `facts_snapshot.agreed_rate_at`), and the ledger bills only meetings the customer accepted (automatic acceptance at the deadline only when the order says so). `sales.call_price_period` (view) lists each customer's price per ICP (`rate_rule` `icp`, `future_icp`, or `default` with `icp_id` NULL) with `valid_from` / `valid_to`, from the orders they adopted.
- Onboarding call price estimate: `POST /api/v1/onboarding/session/{id}/call-price-estimate?wait_seconds=0..10` (the session's user; pay-per-call setups only, else 409) counts the companies of `sales.company` matching the saved questionnaire's industries, company size and markets (free text resolved to ISO codes by `services/market_codes.py`; cities and regions not counted), capped at 20,000, and prices the pool with `call_price_cents_for_pool` (EUR 150 up to 500 companies, EUR 70 from 20,000, log scale in EUR 10 steps). Returns `status` (`running | ready | failed`), `pool_size`, `pool_capped`, `price_cents`, `filters`. Counted once per session and filter scope (`onboarding.call_price_estimate`), in a task detached from the request, 30 s statement timeout; a failed scope stays failed. The onboarding order (`build_onboarding_agreement_order`) sets `prices.future_icp_price_cents` to the ready estimate of the owner's current filters, adds `prices.estimate` (count, filters, disclaimer) and keeps `default_call_price_cents` at EUR 70; with no ready estimate it is EUR 70 and has no `estimate`. Editing the filters changes the order, so it must be signed again. A charge waits three days from the call, and at least three days from when it is recorded (`held`, `CONTEST_WINDOW`), in which any user of the customer can contest it (`POST /api/v1/app/calls/charges/{id}/contest`; `GET /api/v1/app/calls/charges?from&to` lists them by call date with their owner and totals, the amounts only for owners, billing admins and managers: `viewer.can_see_amounts`; `GET /api/v1/app/calls/billing-model` says whether the customer pays per call; `GET /calls/billing-status` carries each company's `charge_id` for the board), before `background_jobs/call_billing.py` posts it as a Stripe pending invoice item on the customer's subscription, which the monthly invoice collects. `sales.call_charge` is the only record of charged calls. The model follows the linked Stripe subscription (its `simpl_pay_per_call_account` line), set by `link_stripe_subscription` and payment-link completion. Admin routes: `/api/v1/admin/customers/{id}/call-charges` (list, void, credit, retry, manual add, `{charge_id}/resolve` for a contested one), `/admin/customers/{id}/call-pricing`, `/admin/icps/{id}/call-price`, `/admin/call-pricing/quote`, `/admin/call-pricing/icps`; payment links, `POST /admin/customers/{id}/subscription/create` and onboarding `billing_options` take `product = "pay_per_call"`. Stripe objects: `scripts/stripe_setup_pay_per_call.py`.
- The admin outreach case view reads (all `require_admin`, read-only): `GET /api/v1/admin/customers/{id}/call-charges` takes an optional `company_id` and each charge also says `created_at`, `updated_at`, `contested_by` (+ `contested_by_name`), `resolved_by`, `resolved_at`, `ulc_id`, `history_id`, `claimed_at` (the Stripe posting claim) and `owner_user_id` / `owner_name` (the app's Calls tab shows customers exactly what it did); `GET /api/v1/admin/customers/{id}/companies/{company_id}/meetings?past_days=365&future_days=90` (caps 730 / 180, 422 beyond) lists the customer's calendar meetings with the company's leads from Recall's synced calendars (simpl_core `LeadMeetings.for_lead`; the company's leads and the customer's connections at it, with an email address, at most 200: `leads_checked`, `truncated`), one row per `meeting_key` with its `lead_ids`, 404 for an unknown company, never written to `sales.meeting_booking`; `GET /api/v1/admin/conversations` gives every message `journey_log_id` (`provider_metadata.journey_log_id`, emails only today) and `provider_message_id`, null when absent. `migrations/20261004_case_view_read_grants.sql` grants the service role `SELECT` (only) on `sales.call_charge` and `sales.call_held_evidence` for the dashboard's direct reads.
- Changing a customer's plan (platform admins): `POST /api/v1/admin/customers/{id}/subscription/switch` with `target` (`standard | growth | pay_per_call | managed`), a caller-chosen `switch_id` (resending it resumes the same switch) and `preview: true` for a dry run (steps, seats, open invoices, the old plan's final-invoice credit, warnings). In one operation it creates the new subscription (or a checkout link when there is no card, `outcome: awaiting_payment`; the old subscription is canceled when the link is paid), points the row at it with `billing_model` / `billing_model_since`, optionally voids the old plan's open invoices (`void_open_invoices`) and cancels the old subscription now with proration. Seats and access never change during the switch. Logic in `services/plan_switch.py`. `POST .../subscription/cancel-now` (`stripe_subscription_id?`, `prorate`, `void_open_invoices`) cancels the linked subscription, or another live one of the same Stripe customer, immediately. `POST .../subscription/create` takes `replace_existing` and `cancel_replaced`, `POST .../subscription/link` takes `cancel_replaced`, and `GET .../subscription` lists `other_subscriptions` (live Stripe subscriptions the row does not point at). A trial payment link refuses (409) a customer with a live subscription unless `replace=true`. ## Common pitfalls

- Do not duplicate shared logic already available in `simpl_core`.
- Do not add undocumented environment variables.
- Do not run real external provider calls in tests unless explicitly marked/configured.
- Do not give a challenge endpoint a product guard, or a product endpoint `require_challenge_participant`. The two contexts are separate types precisely so the substitution does not typecheck.
- Do not send a price, promotion code or return URL to the payer's `POST /api/v1/onboarding/session/{id}/checkout-intent`: `price_override`, `promo_override`, `success_url` and `cancel_url` are ignored and logged. An admin sets a custom price or code in the setup invite's `billing_options`, and Stripe always returns to `ONBOARDING_PUBLIC_BASE_URL/onboarding?checkout=success|cancel`. `.../subscription/confirm` accepts only the checkout that session's checkout-intent created.
- Onboarding helpers for the invited flow: `POST /api/v1/onboarding/session/{id}/website-brief` reads the session's company website (Firecrawl/Jina scrape plus the first-run quick-context turn, traced as `first_run_quick_context`) and returns editable answers (`status: ok | unreadable | no_source`, `value_proposition`, `summary`, `target_roles`, `target_geographies`, `company_size_min/max`); nothing is saved. `GET|POST /api/v1/onboarding/session/{id}/team-invites` (`{invites: [{email, role}]}` up to 20; role `sales_user` (sending account), `manager` (admin) or `billing_admin` (billing manager, invited with `requires_payment=false`: the owner still pays)) lets the person setting up a new customer (invite role `owner`, `manager` or `billing_admin`) invite teammates on the session's customer setup before the customer exists; each address succeeds or fails on its own (`{sent, failed}`), and a session without a pending/ready setup gets 409. The owner can hand the card to a billing manager: `POST /api/v1/onboarding/session/{id}/payment/delegate {email}` invites (or upgrades) a paying `billing_admin` with the owner's billing options and closes the owner's card step; `POST .../payment/delegate/cancel` takes it back until a card is connected. The snapshot exposes `context.payment_delegation`. Checkout-intent refuses a session that does not pay and any setup that already has a card.

## Operational alerts

- `simpl_api.startup.agent_framework_failed` posts to Discord #error when the agent framework wiring fails at startup. The deploy does not come up.
- Agent framework failures reach #warning once. Chat alerts carry `user_id`, `customer_id`, `conversation_id` and `turn_id`; challenge alerts carry `participant_id`, `contest_id`, `scenario_id` and `turn_id`; Sales Domain wake alerts carry `user_id`.
- `agent_framework.engine.validator_failed` in `pipeline_ops_agent` is promoted to #error. The rule is registered additively, so another app's rules registered in the same process stay in place.
- Requires simpl_tracker `f581b40` or later (notify API version 3, report-once through `raise ... from`, the `__simpl_notify__` silent marker) and simpl_core `855253e` or later (`add_alert_rules`, `labels` on the Sales Domain wrappers).
