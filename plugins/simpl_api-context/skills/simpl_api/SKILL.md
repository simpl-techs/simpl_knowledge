# simpl_api integration guide

> **Maintained by**: the `simpl_api` repo, auto-synced to simpl_knowledge.
> **Source of truth**: `simpl-techs/simpl_api/.agent/SKILL.md`

## What this service is

`simpl_api` is the FastAPI backend for the simpl sales intelligence platform. It exposes app/admin API routes, webhook handlers, guided/autopilot endpoints, prompt/template services, background jobs, and agent-facing backend workflows.

## Installation

```bash
conda env create -f environment.yml
conda activate simpl_api
poetry install
cp .env.example .env
```

This repo is normally deployed as a service, not installed as a dependency by other repos.

## Basic usage

```bash
conda activate simpl_api
poetry run uvicorn simpl_api.main:app --reload
```

When adding API behavior, place HTTP route code under `src/simpl_api/api`, reusable business logic in `simpl_core` or `src/simpl_api/services`, and schemas under `src/simpl_api/schemas`.

## Rules and conventions

- Keep FastAPI route handlers thin. Move reusable domain behavior to `simpl_core` or a service module.
- Use Pydantic schemas for request/response contracts.
- Keep environment variables documented in `README.md` and `.env.example` when adding new config.
- Use existing agent/service patterns before introducing a new orchestration style.
- Emails a user's SimpL agent sends go through the `email` channel plugin and `services/channels/agent_email.py`: a plain email in the agent's words, one link into SimpL, signed as the user's own agent persona. Pass `brain.notify_user` a `body` (and optionally `subject`, `route`); don't build HTML.
- A seller's active hours, when the extension may send, are `outreach_prefs.active_hours` = `{"start": "HH:MM", "stop": "HH:MM", "timezone": "<IANA name>"}` (start inclusive, stop exclusive, start before stop). A missing field takes 07:00 / 19:00 / UTC, and an unset or invalid window runs on 07:00-19:00 UTC. `sales.resolve_active_hours(prefs jsonb[, at timestamptz])` resolves it: the extension task RPC gates on it, and `GET`/`PATCH /api/v1/app/preferences` return its answer as `active_hours_effective` (`start`, `stop`, `timezone`, `source` = `configured` | `unset` | `invalid`, `is_open_now`). `PATCH` merges `active_hours` one level deep, `null` resets it, and a value the resolver calls invalid, or a zone not spelled exactly as in IANA, is refused with 422. Read the window through the resolver (`services/active_hours.py`) instead of re-parsing the JSON. Review-answer follow-ups (`review_response_service._next_business_morning`) schedule at the start of the seller's window, 09:00 Europe/Rome without one, like simpl_core's retry triggers (simpl_core >= 0.8.2).
- Authenticate product routes with `auth.get_current_user`, which also refuses SimpL Challenge entrants; scope them with `simpl_api.guards`, whose `resolve_user_context` repeats that refusal against the database. Both are single places, so a new endpoint written against the ordinary dependencies inherits them. Do not reimplement either check per endpoint.
- Approval routes (journey-log `set-pending`, managed approve, Agent API draft approve and `bulk-approve`) and invite execution return the status the database settled on. simpl_core's dispatch authority rule can send an approved row back to `PENDING_APPROVAL` (`payload.authority.block_reason`) or cancel it, so callers must not assume `PENDING`; `bulk-approve` lists such rows under `withheld`, and invite execution answers 409.
- A colleague's hand-off is passed on from one of its cards: `GET /api/v1/app/journey-log/{id}/handoff-redirect` returns the objective behind the card (`objective_id`, `responsibility_key`, `state`) and the colleagues it can go to (`targets[]`: `user_id`, `full_name`, `responsibility_key`, `description`). `POST` with `{to_user_id, reason?}` moves it (simpl_core `AccountCoordinationService.redirect`). The targets come from the team table, not from the caller. The old hand-off closes and its queued cards are cancelled, and the new owner is woken. A card that isn't the caller's, or has no `coordination_objective_id`, gets 404. A colleague the table does not allow gets 403, naming the allowed ones. A closed hand-off, or an open one already on the target's responsibility, gets 409. Repeating the same move replays it (`replayed: true`). Managed operators have the same pair at `/api/v1/admin/managed/actions/{id}/handoff-redirect`: the managed-scope check resolves the card's owner, the move is made as that owner, and the operator is recorded in `sales.audit_log` (`managed.action.handoff_redirect`).

- The funnel's ROI block is `POST /api/v1/app/reports/value` and `POST .../value/seat-request`. It is a staff beta: only SimpL staff (`is_admin`) get it, 403 for everyone else, and the response says `beta: true`. Setting `ROI_RELEASED_TO_CUSTOMERS=true` (also `1`/`yes`/`on`) in the API environment releases it to the customer's owners, billing admins and ICP managers; unset or any other value keeps it staff-only. The cost follows the model Stripe bills (a pay-per-call account line means pay per call; the database model only when Stripe cannot say). Staff can send `simulate_pay_per_call: true` to price a seat customer as if it paid per call (`simulated: true`, `viewer.can_simulate`); anyone else gets 403. The seat request is how ICP managers ask owners and billing admins for accounts through the governed in-app notification. `rolling` (7, 30, 90) is the window of the funnel metrics beside the block and `offset` (0-104) moves it back that many windows; the response's `period` is that window itself, not a pace: its leads and meetings, the new customers its meetings bring at the close rate, their value, what SimpL cost in it (seats: the subscription for its days at today's price; pay per call: the calls charged in it) and `roi`, with `has_earlier` to stop going back at the first lead, or at the window pay per call began in (`cost_counted_from` set, `roi` empty: the seats paid before are unknown). The monthly figures and the forecast are that window's pace. All arithmetic lives in `services/customer_value/model.py`. `sales.icp.deal_size` means the yearly value of one new customer won from that ICP, in the customer's billing currency; it is set with `PATCH /api/v1/app/icps/{icp_id}/deal-size`, and the ROI prefers it over the median of `sales.deal`.
- Billing runs without rollout switches: the pay-per-call cycle (record, fifteen-day contest window, Stripe posting, invoices), the hourly Growth price transitions and the call-evidence moves into Negotiation always run. What a customer pays is decided per customer, by its billing model and its Stripe subscription. An account that must pay nothing (SimpL's own) is a pay-per-call customer in billing mode `comp`, a 100% coupon on its subscription: its calls are recorded, posted and invoiced like anyone's, at zero. The call-evidence job applies the evidence of the last 30 days it has not applied yet, at most 500 per run.
- Pay per call (`sales.customer_subscription.billing_model = 'pay_per_call'`): accounts are free and each company is charged once, when its first call that took place is attributable to SimpL (`sales_view.billable_calls`: the company moved into Negotiation, or into Closed after a meeting, and the customer claimed it and wrote to it before the meeting), from `billing_model_since` on, at its ICP's `sales.icp.call_price_cents`, EUR 70-150 in 10 EUR tiers from the pool size (`services/call_pricing.py`). A charge waits fifteen days (`held`, `CONTEST_WINDOW`), in which any user of the customer can contest it (`POST /api/v1/app/calls/charges/{id}/contest`; `GET /api/v1/app/calls/charges?from&to` lists them by call date with their owner and totals, the amounts only for owners, billing admins and managers: `viewer.can_see_amounts`; `GET /api/v1/app/calls/billing-model` says whether the customer pays per call; `GET /calls/billing-status` carries each company's `charge_id` for the board), before `background_jobs/call_billing.py` posts it as a Stripe pending invoice item on the customer's subscription, which the monthly invoice collects. `sales.call_charge` is the only record of charged calls. The model follows the linked Stripe subscription (its `simpl_pay_per_call_account` line), set by `link_stripe_subscription` and payment-link completion. Admin routes: `/api/v1/admin/customers/{id}/call-charges` (list, void, credit, retry, manual add, `{charge_id}/resolve` for a contested one), `/admin/customers/{id}/call-pricing`, `/admin/icps/{id}/call-price`, `/admin/call-pricing/quote`, `/admin/call-pricing/icps`; payment links, `POST /admin/customers/{id}/subscription/create` and onboarding `billing_options` take `product = "pay_per_call"`. Stripe objects: `scripts/stripe_setup_pay_per_call.py`.
- SimpL Growth: seats at an intro price for N months, then a regular price (defaults EUR 200 x 3 months, then EUR 350, per seat per month, VAT on top). Plan defaults: `GET /api/v1/admin/billing/plans`, `PUT /api/v1/admin/billing/plans/growth` (platform admins). Payment links, `POST /admin/customers/{id}/subscription/create` and onboarding `billing_options` take `product = "growth"` with `intro_price_eur`, `intro_months`, `regular_price_eur` (left-out terms take the defaults). A live Standard subscription moves to Growth in place with `POST /api/v1/admin/customers/{id}/subscription/growth` (`effective: next_renewal | now`, `dry_run`), its price changes with `POST .../subscription/growth/price`, and `GET /admin/customers/{id}/subscription` returns its state under `growth`. Stripe objects: `scripts/stripe_setup_growth.py`.
- Plans & prices: `GET /api/v1/admin/billing/plans/overview` (platform admins) returns every plan on sale (`standard`, `growth`, `managed`, `pay_per_call`, plus `other` when a live subscription sits on a price the catalog does not know) with its list prices, its totals (customers, paying customers, billed seats, net MRR, by the Business definitions) and one row per live subscription on it (payment state, seats, seat price, MRR, renewal, discounts, `growth` state, `pay_per_call` model and ledger totals). A pay-per-call row also says what its next invoice carries: `open_calls` / `open_amount_cents` (billable charges not invoiced yet, `held` included, at their call prices), `call_discounts` (the subscription's discounts still running at the renewal) and `open_due_cents` (after them; 0 for a 100% gift, null with no live subscription). The `pay_per_call` plan sums those over the customers its totals count in `calls` (`calls`, `amount_cents`, `due_cents`); other plans have `calls: null`. `growth_defaults` carries the Growth terms on sale. It reads the snapshot `/admin/business/*` reads: refresh it with `POST /admin/business/refresh`. It does NOT change a plan or a price.
- ICP cards: `GET /api/v1/admin/customers/{id}/icp-snapshot?days=30` (admins, 1-90 UTC days ending today) returns, per ICP of the customer: `pool_size` (companies matching it today), `proposal_days` / `claim_days` (dense per UTC day: companies proposed to its users, distinct per day; connections created) with their sums, all-time `meetings`, `calls_held`, `closed` from `company_funnel_facts` plus the window's `meetings_in_window` / `calls_held_in_window` (a company counts under the ICP it was first claimed from), `users` (assigned, with `is_active`, `daily_lead_limit`, `autopilot_enabled`), `setup` (enabled filters, industries and signals, roles, workflow name, verification, cross-ICP exclusion) and `call_pricing` (price, its source, the pool it was priced at, and the billable charges the ledger priced at it). One read for every ICP; `GET /admin/icps/{id}/stats` stays the single ICP's deep view.
- Calls with leads (`/api/v1/app/calls`): `POST /confirm` records whether a call took place (`{company_id | ulc_id, outcome: held | no_show | rescheduled, held_at}`); held moves the owner's leads at the company into the workflow's Negotiation stage, dated by the call (409 when the workflow has none). `GET /pending-confirmation` lists the caller's companies in Meeting Booked; `GET /billing-status` says, for a pay-per-call customer, whether each company's call is billable, why not, and where its charge stands.
- LinkedIn voice messages: `POST /api/v1/app/extension/voice-transcripts` (raw audio body, max 3 MiB, container read from the bytes) returns `{transcript}` for the extension, through the simpl_sales proxy at `/api/v1/linkedin_data/voice_transcript`. Auth is `get_current_user` plus `require_extension_access`. Optional `?event_urn=` (the LinkedIn event) and header `x-simpl-extension-version` are only kept on the outcome row. Nothing is retried and the transcript is never stored: 413/415 refuse the audio before any paid call, 502 means the provider failed, 422 an empty transcript, and in every case the extension simply does not send that voice. Each request past the access check leaves one `app.operation_log` row (see Operation log). The cost goes through `simpl_tracker.clients.openai_audio.transcribe_audio` (`gpt-4o-mini-transcribe`, process `linkedin_voice_transcription`): tracker transport accounting does not see transcriptions, so do not call `audio.transcriptions.create` directly.
- Operation log (`app.operation_log`, `services/operation_log.py`): one row per outcome of a best-effort operation that can drop something unnoticed (`operation`, `outcome` succeeded/skipped/failed, `reason` code, `subject`, `source`, `client_version`, small flat `details`). simpl_api endpoints write their own rows with `record_operation` (source `simpl_api`); the extension reports what the backend never sees, e.g. a voice it could not download, through `POST /api/v1/app/extension/operation-logs` (source `extension`, `get_current_user` plus `require_extension_access`, 204), behind the simpl_sales proxy `/api/v1/extension/operation-logs`. Allowed operations are the `Operation` literal in `services/operation_log.py` (today `linkedin_voice_transcription`): a new use case adds its name there, no migration. Writing a row never raises and never fails the operation it describes; nothing reads the rows to decide anything. Migration `migrations/20261002_operation_log.sql` (backend-only, RLS on).
- Meetings and calls are counted once, the same everywhere: `sales_view.company_funnel_facts(customer_ids, since)` (a company's first booking, its first call that took place, and whether SimpL brought it). `POST /api/v1/admin/reports/customers-metrics-overview` returns `meetingBookedInPeriod`, `meetingsAttributableInPeriod`, `callsHeldInPeriod`, `callsBillableInPeriod` per customer in the request's `timezone`; `POST /api/v1/app/sales-metrics/metrics` takes `timezone` and returns `meetingsBookedInPeriod`, `meetingsBySimplInPeriod`, `callsHeldInPeriod`, `callsBillableInPeriod` (the user's own with `scope: user`). `meetingBooked` / `closed` there are where companies stand today, whatever the period.

## Common pitfalls

- Do not duplicate shared logic already available in `simpl_core`.
- Do not add undocumented environment variables.
- Do not run real external provider calls in tests unless explicitly marked/configured.
- Do not give a challenge endpoint a product guard, or a product endpoint `require_challenge_participant`. The two contexts are separate types precisely so the substitution does not typecheck.
- Do not send a price, promotion code or return URL to the payer's `POST /api/v1/onboarding/session/{id}/checkout-intent`: `price_override`, `promo_override`, `success_url` and `cancel_url` are ignored and logged. An admin sets a custom price or code in the setup invite's `billing_options`, and Stripe always returns to `ONBOARDING_PUBLIC_BASE_URL/onboarding?checkout=success|cancel`. `.../subscription/confirm` accepts only the checkout that session's checkout-intent created.
- Onboarding helpers for the invited flow: `POST /api/v1/onboarding/session/{id}/website-brief` reads the session's company website (Firecrawl/Jina scrape plus the first-run quick-context turn, traced as `first_run_quick_context`) and returns editable answers (`status: ok | unreadable | no_source`, `value_proposition`, `summary`, `target_roles`, `target_geographies`, `company_size_min/max`); nothing is saved. `GET|POST /api/v1/onboarding/session/{id}/team-invites` (`{invites: [{email, role}]}` up to 20; role `sales_user` (sending account), `manager` (admin) or `billing_admin` (billing manager, invited with `requires_payment=false`: the owner still pays)) lets the person setting up a new customer (invite role `owner`, `manager` or `billing_admin`) invite teammates on the session's customer setup before the customer exists; each address succeeds or fails on its own (`{sent, failed}`), and a session without a pending/ready setup gets 409. The owner can hand the card to a billing manager: `POST /api/v1/onboarding/session/{id}/payment/delegate {email}` invites (or upgrades) a paying `billing_admin` with the owner's billing options and closes the owner's card step; `POST .../payment/delegate/cancel` takes it back until a card is connected. The snapshot exposes `context.payment_delegation`. Checkout-intent refuses a session that does not pay and any setup that already has a card.

## Operational alerts

- `simpl_api.startup.agent_framework_failed` posts to Discord #error when the agent framework wiring fails at startup. The deploy does not come up.
- Agent framework failures reach #warning once. Chat alerts carry `user_id`, `customer_id`, `conversation_id` and `turn_id`; challenge alerts carry `participant_id`, `contest_id`, `scenario_id` and `turn_id`; Sales Domain wake alerts carry `user_id`.
- `agent_framework.engine.validator_failed` in `pipeline_ops_agent` is promoted to #error. The rule is registered additively, so a process that also embeds simpl-outreach keeps both apps' rules.
- Requires simpl_tracker `f581b40` or later (notify API version 3, report-once through `raise ... from`, the `__simpl_notify__` silent marker) and simpl_core `855253e` or later (`add_alert_rules`, `labels` on the Sales Domain wrappers).

## Testing

No work in `simpl_api` should be considered complete until the full repo test suite has been run successfully. Targeted tests help during iteration, but they do not replace the final full-repo run. [per simpl-testing-policy]

```bash
conda activate simpl_api
poetry install
poetry run pytest
poetry run ruff check .
```

## What this service does NOT do

- Does not own reusable platform domain primitives. Put those in `simpl_core`.
- Does not own database ORM primitives. Use `simpl_orm`.
- Does not schedule long-running Prefect workflows. Use `simpl_flow`.
- Does not own frontend UI. Use `simpl_sales` or `simpl_dashboard`.

## Where to go next

- Source: `https://github.com/simpl-techs/simpl_api`
- App routes: `src/simpl_api/api`
- ROI admin: `src/simpl_api/api/v1/admin/roi.py` (domain in `simpl_core.roi`). People/expenses routes use `require_owner`. `PUT /admin/roi/people` mints the person's `survey_token` when missing and does **not** write `roi.people_costs` — those rows come from `POST /admin/roi/people-costs/rebuild`, which rebuilds the table from PAYROLL bank lines (every `PUT` also triggers that rebuild). An employee month costs gross from RAL plus employer INPS/INAIL/TFR, not the net paid; `from_month` is the first day worked and prorates that month; `inps_relief_monthly` / `inps_relief_months` waive employer INPS for a hiring incentive. Fields absent from the JSON body are left untouched on an existing roster row (so a save that only sends name/RAL does not clear `from_month` / `to_month`). `POST /admin/roi/people/{person}/survey-token` mints one on demand; existing tokens are never rotated. `GET /admin/roi/people` is read-only and returns `survey_token: null` for whoever has none yet.
- Managed Operations fleet: `GET /api/v1/admin/managed/operations/fleet` in `src/simpl_api/api/v1/admin/managed.py`, logic in `src/simpl_api/services/operations_fleet.py`. Scope defaults to everyone active at a customer with an active managed engagement; `engagedOnly=true` narrows it to the people pinned to the engagement; `allCustomers=true` covers every active person at every active customer, managed or not. `POST`/`DELETE /admin/managed/engagements/{engagement_id}/users/{user_id}` pin or unpin one person (the invoiced seats follow the engagement's own `seat_count`, untouched here). Deactivated users and users of deactivated customers are never included. Per person it returns `autopilot` (state working/failing/idle/not_running/off, last run, blocker), `pipeline` (7-day reviews), `limits` (account stage, daily company supply, invite/message/email limits, mailbox status), `days` (7 UTC day buckets: suggested, reviewed, claimed, sends and failures per channel, accepted invites, replies, limiter counters and that day's capacity), `activity` (the window's sums), `alerts` (`kind`, `severity` critical/warning, `title`, `detail`) and `queue` (message drafts vs requests). Customers and the summary roll up `days`, `limits`, `activity` and `alerted_people`; the summary's own `alerts` hold fleet-wide problems such as no companies generated today.
- SimpL Challenge observability (read-only, `require_admin`): `GET /api/v1/admin/challenge/overview`, `/participants?include_sandbox=`, `/participants/{id}?version=` in `src/simpl_api/api/v1/admin/challenge.py`. Stage, flags and the automatic score (not calibrated: never rank with it) are defined in `docs/challenge-admin-api.md`.
- Dashboard roles: `src/simpl_api/api/v1/admin/platform_roles.py`. Hierarchy: owner > admin > staff. `is_admin` is derived.
- Admin reports: every `/api/v1/admin/reports/*` route (`src/simpl_api/api/v1/admin/reports.py`) requires `require_admin` and answers 403 to anyone else; they take any customer or user id. Customer apps use the scoped `/api/v1/app/reports/*`.
- ROI vendor catalog: migration `20261001_roi_vendor_catalog.sql` adds `roi.vendors`, `roi.vendor_aliases`, `roi.vendor_assignments` (domain in `simpl_core.roi.vendors`), `roi.transactions.kind` / `payer`, and the HR line `INI-60` Team e retreat (outside the ROI ranking) for travel and retreats. `POST /admin/roi/transactions/import` (`require_owner`, body `{csv}`, the Revolut Business CSV text up to 5 MB) stores every spend line by Revolut id (a re-upload refreshes, never duplicates) and adds unseen vendors to `roi.vendors` without touching the triage or assignments of known ones (`services/roi_statement.py`). It answers `lines`, `inserted`, `updated`, `skipped` (by reason), `vendors`, `new_vendors` and `vendors_to_classify`; a file that is not a statement answers 400. After storing the lines it groups travel into trips (`services/roi_trips.group_trips`) and reports `trips_joined` / `new_trips`. Trips: `GET /admin/roi/trips` (lines, total, payers), `PUT /admin/roi/trips/{id}` (`initiative_id`, optional `name`; refuses a closed, merged or unpublished row), and `POST /admin/roi/trips/{id}/release` (`transaction_ids` that were not travel; they leave the trip for good and go back to vendor classification; refused whole if one is not in that trip). It does not apply tagging rules or rebuild people costs: those stay their own calls. The same migration lets a ledger row name a `person` instead of an `initiative_id`. That share follows the person's survey hours, and the ROI overview reports the part with no hours to follow as `undistributed` (by person).
- ROI vendor upkeep (`services/roi_vendors.py`, `require_owner`). A new vendor met at import or apply gets a first triage from its merchant codes and lands in the reviewer's quiz (`reviewer_for(area)`: tech goes to Raffaele, everything else to Luca).
  - `GET /admin/roi/vendors`: every vendor with spend, the decision in force today, history and aliases.
  - `PATCH /admin/roi/vendors/{key}`: `name`, `area`, `reviewer`.
  - `POST /admin/roi/vendors/{key}/assignments`: `valid_from`, `mode`, `initiative_id`, `people`. A change of use from a date; earlier lines keep their decision.
  - `POST /admin/roi/vendors/{key}/merge`: `into`. Folds a duplicate that has no decision.
- ROI classification: `POST /admin/roi/rules/apply` (no body) runs `services/roi_classify.apply_vendor_rules`.
  - It registers any vendor the catalog lacks (lines loaded before the catalog), then applies vendor and trip decisions to every line as rule-sourced attributions. Manual ones always win, and a rerun writes nothing.
  - It then rebuilds `roi.people_costs`, since the set of PAYROLL lines may have changed.
  - It answers `classified`, `unchanged`, `protected`, `pending` (counts by reason) and `people_cost_rows`.
  - Migration `20261003_roi_vendor_rules.sql` turns off the 115 old text rules and creates the transit row `NON-SPESA` for transfers to our other account. What the old rules wrote stays in the ledger until the engine decides the same line.
  - `POST /admin/roi/attributions` with `remember: true` now writes a vendor assignment (the whole vendor, from the start) instead of a text rule; the `pattern` field is gone.
- ROI vendor quiz (token, not JWT; the person's survey token): `src/simpl_api/api/v1/roi_vendor_quiz.py`, service `services/roi_vendor_quiz.py`, page `/roi/fornitori/<token>` in simpl_dashboard.
  - `GET /roi/vendors/quiz?token=` lists the vendors whose `reviewer` is that person, largest spend first, with spend, payers, samples, the proposal and the current answer. It also returns the live catalog (COGS included), the roster and, for Luca only, the trips.
  - `POST .../answer` writes a vendor assignment valid from the start. It refuses a vendor that is not the person's, an unknown mode, a dead initiative or a person not on the roster.
  - `POST .../accept` confirms the proposals of the listed vendors that have no answer yet; it never overwrites an answer.
  - `POST .../pass` hands a vendor along the chain Raffaele, then Nicolò, then Luca.
  - `PUT .../trips/{id}` and `POST .../trips/{id}/release` decide trips; only Luca can call them.
  - Admin: `GET /admin/roi/vendors/quiz` returns progress by reviewer.
  - Migration `20261002_roi_vendor_quiz.sql` adds the `payer` mode and `roi.vendors.proposed_*`. It also seeds a reviewer and a proposal for every vendor on the Nov 2025 – Sep 2026 statement, plus the aliases that fold duplicates. The seed never overwrites a vendor that already has a reviewer.
- ROI time survey (token, not JWT): `src/simpl_api/api/v1/roi_survey.py`. `GET /roi/survey/bootstrap` and `GET /roi/survey/week` accept `week` (snapped to Monday) and `copy=true` to reuse the previous compiled week without writing it. Both answer only with allocations the person can still allocate onto: an initiative closed or merged after the fact is dropped from the payload, because it is no longer in their catalog and `POST /roi/survey/week` would refuse it and lock them out of the week. The bootstrap also answers `retro_pending` and `retro_quarters` (`[{id, label}]`): the one-shot retro for paid months before the weekly survey (`WEEKLY_SURVEY_START`, 2026-08-31) that no survey week reached. Who gets it comes from `roi.people_costs` and `roi.time_weeks`, not from a list of names; `label` names the months the window really covers (`Nov–Dic 2025`, `Lug–Ago 2026`). `POST /roi/survey/retro` takes `quarters: [{quarter, allocations}]`, needs every pending quarter, validates them all before the first write, fills only the weeks still empty and stamps `roi.people.retro_completed_at`, after which the retro is never offered again (a second save answers 400). `POST /roi/survey/proposals` keeps the proposer's `note` (returned to the admin queue as `note`) and refuses a sixth pending proposal from the same person.
- ROI proposal decisions: `POST /admin/roi/proposals/{id}/decide` takes `action` = `publish` | `reject` | `recategorize` and answers with `decided_by` / `decided_at`, both stored on the row. Publishing under a different `parent_id` re-derives `category`, `lag_profile`, `roi_ranked` and `sort_order` from that line via `simpl_core.roi.catalog.child_defaults` — the same helper the create path uses, so the two cannot drift.
- ROI catalog merge (`require_platform_admin`): `GET /admin/roi/initiatives/{id}/time` lists who filed time on a row (`person`, `weeks`, `pct_avg`). `POST /admin/roi/initiatives/{id}/merge` takes `into` and an optional `redistribute: [{person, allocations: [{initiative_id, share}]}]`; everyone not named follows the merge onto `into`, and each named person's time on the row is split by `share` (each in (0, 100], summing to 100). The whole request is validated before the first write: a person with no time on the row, a person named twice, a destination that is closed, merged or still awaiting review, or `into` being one of the row's own projects answers 400 and changes nothing. A line's open projects move under `into` (re-deriving category, lag, ranking and sort order via `child_defaults`), and merging a line that has projects into a project is refused. The answer lists `redistributed` and `moved_projects`.
- Bank statements: `src/simpl_api/api/v1/admin/bank_statements.py` (logic in `services/bank_statements.py`, tables from `migrations/20261001_bank_statement_import.sql`). The dashboard parses the bank's CSV and `POST /admin/finance/bank-statements` (`require_owner`, **dry run unless `dry_run: false`**) replaces every `financials.ledger` row of `account_id` dated inside `period_start`–`period_end` (or since the beginning when `from_account_opening`), plus any row of the account carrying one of the statement's transaction ids, with the statement's rows — one transaction. Replaced rows are kept whole in `financials.bank_statement_import.replaced_rows`; an outflow category on a replaced row is carried to the new row with the same id, and so is the sync's `external_leg_id` when the replaced transaction was a single leg (the sync and webhook upsert on it); the statement is refused (422) when its balances do not move by exactly its rows (inflows − outflows − fees; from zero with `from_account_opening`); month-end balances go to `financials.account_balance` (`source='statement'`). `PUT /admin/finance/accounts/{id}/balances` types balances (`source='manual'`; `balance: null` removes a typed one, never a statement's). `GET /admin/finance/accounts` and `GET /admin/finance/balances?since=` are `require_platform_admin`. Cash should be summed from balances: the ledger was never complete since each account opened.
