# simpl_foundry integration guide

> **Maintained by**: the `simpl_foundry` repo, auto-synced to simpl_knowledge.
> **Source of truth**: `simpl-techs/simpl_foundry/.agent/SKILL.md`

## What this library is

`simpl_foundry` tracks model training in Postgres and runs it. It owns the `training` schema and its migrations, as `simpl_tracker` owns `cost_tracking`. It depends on `simpl_orm` and `simpl_tracker`; `simpl_core` and training repositories such as `entrex` sit above it. It imports neither `simpl_core` nor `simpl_ia`.

## Installation

```bash
poetry add "simpl-foundry[gcp,hf] @ git+https://github.com/simpl-techs/simpl_foundry.git@main"
```

| Extra | Installs | For |
| --- | --- | --- |
| `gcp` | `google-cloud-storage`, `google-auth` | `gs://` artifact roots and sources, Batch and Cloud Run jobs |
| `hf` | `transformers` | `simpl_foundry.integrations.hf` |
| `lightning` | `lightning`, which brings `torch` | `simpl_foundry.integrations.lightning`, `simpl_foundry.integrations.devices`; `simpl_foundry.integrations.lightning_cli`, with the `jsonargparse[signatures]` it needs |

Install it; do not only put `src` on `PYTHONPATH`. Source readers are found through installed entry points, so without the package's metadata a recipe has no `files` or `table` kind.

`DatasetSnapshot.to_hf` also needs `datasets`, which no extra installs.

## Basic usage (the 90% case)

`simpl_foundry` tracks model training in Postgres (schema `training`, migration
`src/simpl_foundry/migrations/`): one row per **experiment**, found by content,
one row per **run** (a replicate of an experiment), and every logged metric point. The
dashboard's Training section reads these tables. `import simpl_foundry` loads no model
runtime. The trainer adapters need their framework: the `hf` extra for `integrations.hf`,
the `lightning` extra for `integrations.lightning` and the GPU probes.

```python
from simpl_foundry import experiment_identity, init_run, TrainerKind
from simpl_foundry.integrations.hf import HF_NON_IDENTITY_ARGS, SimplCallback

identity = experiment_identity(
    config=config,                                  # the full config as run
    config_exclude=[f"training.{key}" for key in HF_NON_IDENTITY_ARGS] + ["output_dir"],
    code_root=Path("src/entrex"),                   # the training package
    data_files={"records": records_path, "schema": schema_path},
    base_model="example-org/example-model",        # Hub id or a local directory
)
with init_run(project="entrex-ner", identity=identity, config=config, run_dir=output_dir,
              code_root=Path("src/entrex"), trainer_kind=TrainerKind.HF) as run:
    trainer = Trainer(..., callbacks=[SimplCallback(run)])
    trainer.train()
    run.log({"test/f1": f1}, step=trainer.state.global_step)
```

A trainer driven by its own config does this through `tracked_run` (Hugging Face) or `TrackedCLI` (Lightning), from the config's `tracking` section: see *A model repository's trainer, outside a recipe*.

- **Experiment identity.** `experiment_hash` hashes five parts:
  - `identity_version`;
  - the config minus `config_exclude` (dotted paths): names, output paths, logging, machine;
  - the code under `code_root`. Tests, caches and dot files are skipped. A `.py` file is hashed by its syntax tree without docstrings, so comments and formatting do not count;
  - the input files by role and content, not by path;
  - the starting weights: a Hub repository resolved to its commit (the Hub, or the local cache when offline), or a local directory's files.

  The same content is a new run of the same experiment; any change is a new experiment. The environment (package versions, device) is not hashed: it is recorded on each run.
- **`init_run`.**
  - It reads the database settings from the environment (`DatabaseSettings()`, the Supabase variables simpl_flow uses) unless `database=` is given, and raises when they are missing.
  - `offline=True` writes the event log only. Offline, `attach=` and `resume=` need the attempt the caller claimed itself (`attempt=`) and, to resume, the resume point it read (`restorable=`: each alias and the `AliasedArtifact` it points at); without them offline still refuses to attach or resume, and with the database both are refused. An offline attach as attempt n starts its log with `run_attached`, then `run_resumed` past the first attempt.
  - Values the `training` tables refuse raise `ValueError` at the call: a project not matching `^[a-z0-9][a-z0-9_.-]{0,62}$`, a negative step, a metric key not of 1 to 200 characters, an alias not matching `^[a-z][a-z0-9_-]{0,31}$`, a `name` the project already has. A given `name` is checked against the database, so `offline=True` refuses one.
  - `WORLD_SIZE` above 1 raises `ValueError`: a run has one process.
  - Leaving the `with` block finishes the run; an exception fails it, Ctrl-C cancels it, and the exception propagates.
  - Metric values keep NaN and infinities in `training.metrics`; the run's `summary` (last, min and max per key, 200 keys) stores them as the strings `"NaN"` / `"Infinity"`.
- **Training never waits on the database.**
  - The training thread only appends to `<run_dir>/simpl-run/<run_id>/events.jsonl`. A background thread applies new events every 5 s and stamps `heartbeat_at`.
  - An outage of the database or the network only delays the rows; `finish` keeps trying for the drain time.
  - A failure the same events would repeat (an integrity or data error, a malformed event) stops the syncing and logs `training.writer.stopped`.
  - `python -m simpl_foundry sync <events.jsonl | directory>` replays logs and is safe to repeat. A log it cannot apply is reported on stderr, the others go on, and it exits 1.
  - `python -m simpl_foundry sync --run <run_id> --follow [--interval 60] [--max-hours 24]` (`follow.follow_stored_runs`), or `sync --sweep <sweep_id> [--follow]` for the runs of a sweep's job, applies the new pieces of the stored logs every interval until each run has ended, then exits 0; at the cap it exits 1 for a run still open, and 2 for a run it could not follow (an unknown run, a log naming another run). It applies only what is new, each pass in one transaction, and every write is replay-safe, so a follow stopped (Ctrl-C) and started again, or one beside `sync --run` or `collect`, changes no row twice. It prints what each pass applied, and, for a signed run (see *Signed logs*), each object it skipped, once (`follow_stored_runs(report_skipped=)`). `python -m simpl_foundry sync --pending [--max-runs 200] [--max-minutes 10]` (`pending.sync_pending`) is one bounded pass for a schedule, see *Held-out rows, the evaluation job and the scheduled sync*.
  - With an artifact store, a run with the database copies its whole log there at `finish` and `close`, as `logs/<run_id>/<attempt>/events.jsonl`. A run with no database (`offline=True`) stores it in numbered pieces instead, `logs/<run_id>/<attempt>/events-000001.jsonl` and on (`simpl_foundry.log_store`): each holds the complete events appended since the one before, is created only if absent and never rewritten, and the pieces of an attempt, read in order up to the first number missing, are its log. A piece is stored every 60 s when there are new events (`init_run(log_piece_interval=)`), after every stored artifact and at `finish` and `close`; one that cannot be stored is logged and its events go with the next, and the timer thread stops with the run. So a job's log outlives its container and can be read while it trains: `python -m simpl_foundry sync --run <run_id>` applies the stored logs of the attempts from the one the row names on (pieces, else the single `events.jsonl`), in attempt order and in one transaction, and does nothing else. An older attempt is not applied again, as its `environment` events would overwrite the newer attempt's. A resume counts its attempt on the row before it starts (`claim_attempt`), so the row always names the newest attempt: a stored or local log of an older one never ends the run, and a second process resuming the same attempt is refused. A job wrote those logs, so `sync_stored_run` in `simpl_foundry.sync` leaves their `evaluation` events out and refuses a log that names another run, before it applies any; `sweep evaluate` calls it before it ends a run a finished job left open, and passes over a log it cannot apply. A signed run's logs are read only where they verify (see *Signed logs*); `sync_stored_run(on_skipped=)` gets each object it skipped.
- **A run whose process died** stays `running` with its last heartbeat. Readers show it as stalled from `heartbeat_at`; nothing sweeps it.
- **`SimplLogger`** (`simpl_foundry.integrations.lightning`, the `lightning` extra): a Lightning `Logger` over a run, `Trainer(logger=SimplLogger(run))` or appended to `trainer.loggers` from a LightningCLI hook. Keys are grouped like the Hugging Face callback's (`train_loss → train/loss`, `val_f1 → eval/f1`, `test_f1 → test/f1`; a key with a `/` is kept), hyperparameters go to the environment as `lightning_hparams`, and each checkpoint `ModelCheckpoint` saves is stored as `latest` (and `best` when it is the callback's best by its `monitor`); a `last.ckpt` of a step already stored is skipped. `LIGHTNING_NON_IDENTITY_ARGS` lists the `Trainer` arguments to exclude from the identity. It does not end the run.
- **Plain loops** need no adapter: `with init_run(...) as run:` then `run.log({"train/loss": loss}, step=step)`, `run.log_checkpoint(path, step=step)` and `run.log_artifact(model_dir, kind=ArtifactKind.MODEL, aliases=["final"])`.
- **System metrics.** Every 30 s (`init_run(system_interval=…)`, `None` turns it off) a run logs `system/process_rss_gb`, `process_cpu_pct`, `host_available_gb`, `host_used_pct` and `swap_used_gb` (through psutil), with the Unix time in seconds as their step, so every attempt lies on one time axis. The Hugging Face and Lightning adapters add GPU probes (`integrations.devices`: `system/cuda<i>_allocated_gb`, `_reserved_gb`, `_utilization_pct`; `system/mps_allocated_gb`, `mps_driver_gb`); a plain loop adds them with `run.add_device_probe(probe)` for each of `torch_device_probes()`, or its own `DeviceProbe`. A probe that raises is dropped. A CUDA utilization that cannot be read is logged once and left out, and the memory metrics go on.
- **Trained from scratch:** `experiment_identity(..., base_model=None)` records `{"kind": "none"}` as the starting weights.
- **Environment.** A run records its host, platform, Python, the versions of the distributions that change a result, `package_commits` (the `vcs_info.commit_id` of each distribution installed from version control) and `packages_hash`, a hash of every installed distribution, version and commit, what a lock file pins as the process really has it. The trainer adapters add `gpu_type`: the CUDA device's name, `mps`, or `null`, which on a job that asked for a GPU means it ran on the CPU.
- **`SimplCallback`** (the `hf` extra): `loss → train/loss`, `learning_rate → train/lr`, `eval_* → eval/*`, the end-of-training `train_loss → train/mean_loss` (not logged by a trainer resumed from a checkpoint, whose `train_loss` covers only the steps it ran). It records `TrainingArguments.to_dict()` and the device into the run's environment, and only the main process logs. `HF_NON_IDENTITY_ARGS` lists the `TrainingArguments` fields to exclude from the identity.
- **Artifacts** (`artifact_root="gs://bucket/prefix"` or a local directory on `init_run`; GCS needs the `gcp` extra and Application Default Credentials):
  - `run.log_checkpoint(path, step=, best=)` stores a checkpoint as `latest` (and `best`); `run.log_artifact(path, kind=, aliases=)` stores anything else, e.g. the final model as `final`.
  - Files are hard-linked into `<run_dir>/simpl-run/<id>/staging/` before the call returns, so the trainer may delete them or replace them with new files at once, and are uploaded one at a time in the background with a `manifest.json` (every file's size and SHA-256) written last. A file its writer rewrites in place (Lightning's last checkpoint) must be staged with `copy=True`, or the staged copy changes with it.
  - Uploads go oldest first. A newer checkpoint replaces a waiting or failed one whose every alias it takes; an alias stays with the checkpoint of the highest step; a checkpoint left without any alias is deleted from the store; models are never dropped.
  - A failed upload is tried again (`UPLOAD_RETRY_SECONDS`). A model still unstored when a run would finish ends it as `failed`, and `finish` raises `ModelNotStored`, so a job exits non-zero.
  - `log_artifact` raises `FileNotFoundError` for a missing path and `ValueError` for one that holds no data. A file artifact is restored under its own name.
  - `SimplCallback.on_save` writes `simpl_run.json` (run id, attempt, step) into each Hugging Face checkpoint, then stores it this way. `latest_run_checkpoint(output_dir, run_id)` returns the run's own newest checkpoint on disk, ignoring other runs' checkpoints in a shared output directory.
- **Resume.** `init_run(..., resume=<run_id>)` continues a running or stalled run as its next `attempt`, under the same id, and the run's environment takes the new attempt's values. It needs the database and the same experiment (a changed config or code is a new experiment: `ValueError`). An ended run raises `ValueError`. `run.restore_artifact("latest", dir)` downloads what the alias held, every file checked against the manifest (`ArtifactChecksumMismatch`).
- **Code commits.** With `code_root`, the experiment's code is committed under `refs/training/<code_hash>` (git plumbing on a temporary index: the branch, `HEAD`, index and files are untouched; edits to tracked files under the code root and the untracked files of the code manifest are included, so a `.env` is not, `.gitignore` honoured, changed files over 5 MiB left out and named) and pushed in the background. The experiment records `code_commit` and `code_repo` once the remote has it. A job given `SIMPL_CODE_COMMIT` records that commit instead. `snapshot=False` turns it off. A consumer's tests that start a run with a `code_root` inside a real checkout set `SIMPL_CODE_COMMIT` (any 40-hex value), or they push a ref to that checkout's remote.
- **`sync`** also pushes code commits that never reached the remote and uploads artifacts still staged, in the order they were staged, unless the log may belong to a run still running (no `run_ended` and written in the last 5 minutes). A staged checkpoint whose aliases a later step already holds is superseded: not uploaded, recorded as failed, and what an interrupted upload of it left in the store is deleted.
- Migration `src/simpl_foundry/migrations/20261102_training_artifacts.sql` (after `20261023_training_runs.sql`): `experiments.code_commit` / `code_repo`, `runs.artifact_root`, `training.artifacts`, `training.artifact_aliases`.
- **Evaluations.** `log_evaluation(run_id, split=, metrics=, evaluator=, run_dir=)` records a run's scores on one split, on a run still running or long ended. `evaluator_identity(code_root=, code_include=, data_files=, config=)` identifies how a model is judged: the scoring files only (`code_include` patterns, so a trainer change keeps the same identity), the data it reads and the settings that change scores (threshold, label prompts). `eval_hash` adds the split and the metric names. A run has one row per `(eval_hash, split)` in `training.evaluations`: evaluating it again the same way adds nothing, and a changed test set or scorer starts apart. The event goes to the run's log under `run_dir` (a new log when the run's own is elsewhere) and straight to the database; a failed write is returned in `LoggedEvaluation.error`, never raised, and `sync` on its `events_path` writes it later. Scores stay out of the run's summary.
- **Scores per experiment.** View `training.evaluation_scores` (security invoker): per experiment, `eval_hash`, split and metric, the runs evaluated, mean, sample standard deviation, min and max.
- **Metric goals.** `run.define_metric("eval/f1", "max")` records which way a key is better (`runs.metric_goals`); readers fall back to the key's name. Each summary entry also keeps `min_step` and `max_step`.
- **Downsampled series.** `training.metric_series(run_ids, metric_keys, max_points)` (security invoker) returns at most `max_points` points per run and key: a longer series is cut into equal step ranges, each with its last step, mean, min and max of its finite values and its count of NaN or infinite ones.
- **Recipes** (`simpl_foundry.recipe`). A recipe is a YAML file kept next to its trainer, validated by `Recipe` (unknown fields refused): `recipe` (its name), `trainer` (`"package.module:function"`), `trainer_kind`, `base_model`, `data` (`source`, `split`, optional `columns` and named `assets` such as a schema file), `hyperparameters`, `search_surface`, `seed`, `tracking` (`project`, `tags`, `artifact_root`), and optionally `compute` (where a job runs and on what, the same on every target: see *Choosing where a run trains*), `resources` (a Google Cloud job's resources, declared rather than resolved: see *On Google Batch*) and `hub_repositories` (Hugging Face Hub repositories the trainer loads besides `base_model`, staged for a job with no internet). `split` is either `{column, roles: {role: value or [values]}}`, reading the role from a column the rows carry (rows whose value no role names are counted as unassigned and left out), or `{key, seed, shares: {role: fraction, ..., last: "rest"}}`, the role from `sha256(f"{seed}\0{key}")` with the shares taken in order. A recipe holds `shares` as ordered `[role, share]` pairs, which a recipe file may also write; their order is part of the fingerprint. A split needs a `train` role; `train` and `dev` rows go to the trainer, every other role (`select`) is held out from it and only counted. `tracking.project` matches `^[a-z0-9][a-z0-9_.-]{0,62}$`, `seed` fits an INTEGER column, and a key of `objective.simpler` holds a number in the hyperparameters and in its surface choices.
  - **Sources** (`simpl_foundry.sources`): a source is a mapping naming its reader by a key equal to the reader's kind. This package ships `{files: [...]}`, local or `gs://` JSONL or Parquet in order, and `{table: schema.name, columns: [...], where: [...]}`, a platform database table read from the run's `database` (`DatabaseSettings()` by default, also with `--offline`). Each `where` clause is `{column, op, value: {literal: ...}}`, `op` one of `eq ne gt gte lt lte in` (`in` takes a list), every clause must hold, and only literals are accepted. A table read is written to the cache as JSONL in the declared column order with its rows sorted, so the same rows give the same snapshot whatever order they came in and new or changed rows give a new one; timestamps, dates, uuids and decimals become text. Its record in `training.datasets.sources` keeps the table, columns, where and row count; the run's `data.sources` names it `table:<schema.name>`. A missing table or column is a `ValueError` naming it. Other kinds come from other packages: see *Adding a source reader*.
  - **Search surface** (`simpl_foundry.surface`): what a run may change, by dotted hyperparameter path: `{choices: [...]}`, `{range: [low, high]}` (inclusive; `integer: true` for whole numbers) or `{log_range: [low, high]}` (positive). Every key must name a declared hyperparameter whose value it allows. `--set` (and `overrides`) outside it is refused with a `ValueError` naming `search_surface`; anything else is changed by editing the recipe. The surface stays out of the experiment's identity.
  - **Running one:** `python -m simpl_foundry run <recipe> [--set key=value ...] [--seed N] [--run-dir DIR] [--tag T] [--offline] [--if-exists replicate|skip|ask] [--plan]`, or `run_recipe(load_recipe(path), overrides=..., seed=...)`. `--set` takes a dotted key on the search surface (the value read as YAML, `1e-5` as a number). The command first works out the experiment (`plan_experiment`) and prints its existing runs and scores; `--plan` stops there. When the experiment has runs, `--if-exists replicate` (the default) runs another, `skip` starts nothing if a run with this seed finished or is running (a stalled one does not count), and `ask` asks on the terminal (no terminal is no). A refused override exits with code 2. A recipe with no `tracking.artifact_root` takes `SIMPL_TRAINING_ARTIFACT_ROOT` (`recipe.project_placement`, the one a launch uses): the run stores its snapshot, checkpoints and models there, and its row and config name it; with neither, it stores none. With `--offline` it writes no row, and with an artifact root from either source it still stores its artifacts there, and its log in pieces under `logs/<run_id>/1/`.
  - **Launching:** `python -m simpl_foundry launch <recipe> [same options as run] [--on local|batch|cloud_run|leonardo]` works the experiment out as `run` does, then `queue_run(plan, target=...)` builds or reuses the snapshot, commits the trainer's code under `refs/training/<code_hash>` (uncommitted edits included) and pushes it, and writes the experiment and the run as `queued` (`launch_target`, `recipe_hash`, the resolved recipe as config, the snapshot link, and `environment.launch`: target, commit, whether it was pushed, when it was queued and the git state it was launched from). `launch_local(queued, run_dir=...)` then runs the job here, in a temporary git worktree at the commit with the worktree's package first on `PYTHONPATH`, and removes the worktree afterwards. The job is `python -m simpl_foundry job <run id> [--run-dir DIR]` (`run_job`): it reads the run's config and snapshot from the database, refuses a checkout that makes another experiment (naming the part that differs), starts a queued run as attempt 1 (`init_run(attach=...)`, event `run_attached`), resumes a running one as its next attempt and leaves an ended one alone (exit 0, or 1 for a failed run or one canceled for `NoGpu`). On SIGTERM it raises `Terminated`, which closes the run without ending it (`Run.close()`), and exits 143, so a retry resumes the run. A transient failure before the run opens exits 75, for another attempt. A job runs with `SIMPL_TRAINING_RUN_ID`, and with `SIMPL_CODE_COMMIT` / `SIMPL_CODE_REPO` when the commit was pushed. `queue_run` refuses `batch` until the recipe's artifact root is `gs://`; a commit that could not be pushed still runs.
  - **Files-only jobs:** `python -m simpl_foundry launch <recipe> --on local --files-only` runs the job with no database. It needs `tracking.artifact_root` (a directory or `gs://`) or `SIMPL_TRAINING_ARTIFACT_ROOT`, since the job's files there are the run's only record; on Batch and Cloud Run see *Files-only on Google Cloud*. `queue_run` writes every run it queues with an artifact root to `runs/<run_id>/spec.json` there (`simpl_foundry.spec`, format 1): the queued config, the experiment's hashes and data sources, the artifact root, the launch environment, the sweep and when it was queued; `read_spec` gives back what `RunJobState` holds. The job is `python -m simpl_foundry job <run id> --store <artifact root>` (`files_job.run_files_job`), started with every `SUPABASE_*` and `DOPPLER_*` variable removed from its environment. It reads the spec instead of the run's row and never builds `DatabaseSettings`. A stored log of the run holding `run_ended` means nothing runs (exit 1 for a failed run). Otherwise it checks its checkout's experiment, claims attempt n by creating `logs/<run_id>/<n>/attempt.json` only if absent (n is one more than the attempts claimed; a process that loses that race exits 2 and trains nothing), restores the aliases the earlier attempts' stored logs left (pieces, or an `events.jsonl` an earlier version stored), and stores its log in pieces as it trains, after every stored artifact and at its end, so an attempt killed after a checkpoint is resumed from it. The run stays `queued`, with no metrics, until `python -m simpl_foundry sync --run <run id>`, which the launcher prints when the job ends and does not run, or `sync --run <run id> --follow`, which applies the pieces about a minute behind the job. `job --store <dir> --mirror` takes the directory for a copy of the spec's artifact root (`LocalArtifactStore(dir, mirror_of=root)`): the job reads and writes the directory, and what it records, a stored artifact's `uri` and the log's `artifact_root`, names the spec's root, where `collect` uploads the files, so nothing is rewritten. `queue_sweep` writes each sweep's tasks file, `sweeps/<sweep id>/tasks.tsv` (task index, a tab, run id, one line for each task), to the artifact root; `job --sweep <id> --store <root>` finds its run there by `BATCH_TASK_INDEX` or `CLOUD_RUN_TASK_INDEX` (`spec.task_run`), and `sweep run --files-only` runs a sweep's trials so, here, on Batch or on Cloud Run. `queue_run(files_only=True)` records `environment.launch.files_only`. A files-only job stores its artifacts only by creating objects (`init_run(create_only=True)`, `upload_artifact(create_only=True)`): an object an earlier try created counts as stored when its content matches, so a retried upload finishes, and one holding other content fails the upload, which cannot overwrite it. Not yet: stop requests. Other credentials in the launching environment, such as a Doppler token, still reach a local job; the log secret never does.
  - **Files-only on Google Cloud:** `launch <recipe> --on batch|cloud_run --files-only` and `sweep run <recipe> ... --on batch|cloud_run --files-only` run the job as above on Google Cloud, so it holds nothing worth taking: no database login and no secret.
    - **The launch** writes the spec (and a sweep's tasks file) as for any launch and submits a job whose variables carry `SIMPL_TRAINING_STORE=<artifact root>` (`launch.files_only_variables`). The image's entrypoint then runs `python -m simpl_foundry job <run id> --store <root>` (`job --sweep <id> --store <root>` in a sweep's task) directly: it asks the metadata server for nothing, reads no Secret Manager secret and runs no `doppler`. Without that variable it reads the Doppler token and runs under `doppler run` as before; one image serves both. The training repository's lock must pin a simpl_foundry with this entrypoint: an older image's entrypoint takes the Doppler path, which the files-only account cannot read, and its job exits 75 until its retries run out.
    - **The account.** The job runs as `SIMPL_TRAINING_FILES_ONLY_ACCOUNT`, never as `SIMPL_TRAINING_SERVICE_ACCOUNT` or a recipe's own `resources.service_account`: `targets.destination(..., files_only=True)` puts it in the resources and refuses the launch, naming the setting, before anything is queued, built or pushed, when it is unset. The README lists the rights it needs and must not have, with the `gcloud` commands that set them up.
    - **No internet.** With `SIMPL_TRAINING_NETWORK` and `SIMPL_TRAINING_SUBNETWORK` (names in the image's project, both or neither), the resources gain `network` and `subnetwork`: the Batch VM gets no external address in that subnetwork (`allocationPolicy.network`), the Cloud Run task sends all its egress through it (`vpcAccess`, `ALL_TRAFFIC`). In a network with Private Google Access and no Cloud NAT the job reaches Google's APIs and nothing else. Such a job cannot reach the Hugging Face Hub, so the launcher stages what it reads (`hub.stage_hub_files`: `base_model` at the experiment's commit and each of `hub_repositories` at `main`'s commit) under `hub/models--<owner>--<name>/<commit>/` of the artifact root, an artifact with its manifest, staged once for each commit and reused; the run records the pins in `environment.launch.hub`, the job copies them into its Hub cache (`/job/hf`) before loading its trainer, and its variables keep the Hugging Face libraries offline. Without the network settings a files-only job still holds no secret but reaches the internet, and the launcher says so.
    - **Deadline and GPU, from files.** A run whose spec's launch target is `batch` or `cloud_run` keeps its `resources.max_hours` from when its first attempt started, which that attempt's marker records (`StoredLog.first_started_at`): an attempt that starts past it does not train, one that reaches it while training stops (`DeadlineExceeded`, run failed, exit 1). A job that asked for a GPU and sees none does not train (`NoGpu`: canceled when no attempt had run, else failed; exit 2, and a retry exits 1). A refused attempt still claims its number and stores a log that ends the run, so `sync --run` ends it in the database with that status and error type.
    - **Compute.** The job holds no key to record its compute session. The sync that first applies its logs, taking the run out of `queued` (`sync --run`, `sync --follow`, `sweep evaluate`), reports the gap once for the run through `simpl_tracker.report_tracking_gap` (`compute_tracking.files_only`, naming the labels `simpl_repo` and `training_run_id`, or `training_sweep_id` for a sweep's job). It never raises or waits.
    - **Live results.** The launcher prints `python -m simpl_foundry sync --run <id> --follow` (`--sweep <id>` for a sweep) and starts nothing for it. `simpl_foundry resume` of a files-only Batch run submits the same files-only job, with the same key.
    - **Signed logs** (`simpl_foundry.log_signing`, `simpl_foundry.stored_log`). A files-only job may run code no person reviewed, and its account can create objects under every run's `logs/` and `artifacts/` prefixes, not only its own: without more, one job could add log pieces or an attempt marker under another run's prefix and forge its metrics, artifacts and status. So a files-only run on Batch or Cloud Run, and one here when the secret is set, has a signed log. The launcher and whatever syncs hold one secret, `SIMPL_TRAINING_LOG_SECRET`; a launch on Batch or Cloud Run without it is refused, naming it, before anything is queued (`targets.destination`, `log_signing.signing_scope`). A run's key is HMAC-derived from the secret and the run's id; a sweep's job on Google Cloud gets its sweep's key, and each task derives its run's key from that and its run's id. The launcher gives the job its key as `SIMPL_TRAINING_LOG_KEY` and records on the run's row only that the log is signed and what the key comes from (`environment.launch.log_signing`: `run` or `sweep`); no key is stored in the artifact store or the database, and no job's environment gets the secret. The job signs each attempt marker (a `mac` field, `StoredLog.claim`) and each log piece (a last line `{"type": "log_signature", "offset": ..., "mac": ...}`, `init_run(offline=True, log_key=)`) over its content, the run, the attempt and the piece's number, so a valid piece copied to another run, attempt or number does not verify. A job finding another job's object where its next marker or piece goes moves to the next number no object holds, and loses no event; one finding a marker its own run signed there is another process of the run, and exits 2. Everything that reads a signed run's stored log for a decision uses only what verifies with its key: the job reading its earlier attempts (the resume point, whether the run ended, the deadline's start), `sync --run`, `sync --follow`, `sync --sweep` and `sweep evaluate`. An attempt counts when its marker verifies; its log is its verified pieces in number order, each starting where the one before ended. Every other object under the run's `logs/` prefix is skipped and reported once, by the sync that meets it: logged as `training.log.object_skipped` and printed by `sync` as `skipped, not the run's own: <where>: <why>`. A skipped object is one the run's job did not store there; seeing one means another job tried to change the run, and nothing of it was applied. A stored artifact's manifest checksum is in a signed `artifact_stored` event, and both the resume (`Run.restore_artifact`) and `sweep evaluate` check the manifest against it, so files another job created under the artifact's prefix are refused. The events of a signed run's own job never change `environment.launch`. A run not recorded as signed (with the database, on Leonardo, here without the secret, or by an earlier version) is read as before. Limits: the tasks of one sweep train the same code and share its key, so each can sign for the sweep's other runs (never for a run outside the sweep); a job can still create objects under another run's prefixes, which burns attempt and piece numbers there and makes its listings longer, and costs that run nothing else; a job of a run not recorded as signed can still be forged as before. A sync of a signed run where the secret is unset raises `LogSecretMissing`, naming it.
  - **Held-out rows, the evaluation job and the scheduled sync** (`simpl_foundry.pending`, `simpl_foundry.sweep.evaluator_job`):
    - **The held-out root.** With `SIMPL_TRAINING_HELD_OUT_ROOT` (a `gs://` location outside the artifact root; one inside it is refused by `targets.destination`, and by `recipe.held_out_store_for` for `run`), `prepare_data(held_out_store=)` stores a new snapshot's held-out part under `hidden/datasets/<fingerprint>/` there, never under the artifact root, and `training.datasets.hidden_uri` records where it went. `queue_run` and `run_plan` read the setting; no recipe field names it, as a run's config is in its spec. A snapshot stored before keeps its part under the artifact root's `hidden/`, and `hidden_uri` still names it. Evaluation (`sweep.evaluate.held_out_store_of`, used by `evaluate_sweep` and `promote_sweep`) reads the part where `hidden_uri` says. A launch never reads the held-out root (it asks the artifact root whether a snapshot stored before keeps its part there), so whoever launches needs only to create objects in it. Nothing a training job gets names it: its spec, its variables, its Leonardo staging.
    - **The pinned trainer part.** `queue_run` records the checksum of the snapshot's trainer part in the store (its manifest's SHA-256, `PreparedData.trainer_checksum`) as `environment.launch.trainer_checksum` (`launch.TRAINER_CHECKSUM_FIELD`), in the run's row and its spec. A job that downloads the part from the store, with the database or files only, checks the manifest against it and raises `ValueError` (exit 2, nothing claimed) for another; a part in the job's own cache is read as it is. A cached part that is not the stored one (built here apart, other bytes) is replaced by the stored one when a launch prepares the data (`snapshot.stored_trainer_part`), so a Leonardo staging, taken from the cache, matches the pin. A run queued before has no pin and is read as before.
    - **The evaluation job.** `python -m simpl_foundry sweep evaluate <sweep> --on cloud_run [--gpus 1] [--cpus N] [--memory-gb N] [--hours H] [--fail-unscored] [--no-wait]` (`submit_evaluation`) builds the code image (`batch.code_image`) of the repository holding the recipe's evaluator at its current `HEAD`, never a trial's commit, refusing tracked changes under the evaluator's package that `HEAD` lacks, and creates the Cloud Run job `evaluate-<first 12 hex of the sweep id>-<ms>` with one task: the evaluator account `SIMPL_TRAINING_EVALUATOR_ACCOUNT` (refused, naming it, when unset; also needs `SIMPL_TRAINING_REGISTRY` and `SIMPL_TRAINING_REGION`), no GPU unless asked, 4 vCPUs, 16 GB and 2 hours by default (`EVALUATION_COMPUTE`, checked by `platforms.task_problems`: without a GPU 1, 2, 4, 6 or 8 vCPUs, at most 4 GB each, 24 hours), labels `simpl_repo` and `training_sweep_id`, and variables `SIMPL_TRAINING_EVALUATE_SWEEP` (`entrypoint.EVALUATE_VARIABLE`) and `SIMPL_CODE_COMMIT`. It follows the execution as a launch does. The image's entrypoint then runs `sweep evaluate <sweep> --work-dir /job/runs` under `doppler run` with the token of the Secret Manager secret `<REPO>_EVALUATOR_DOPPLER_TOKEN` (`entrypoint.evaluator_doppler_secret`), whose config holds the database, cost tracking and log secret settings. `sweep evaluate` with no `--on` runs `evaluate_here`: `evaluate_sweep` here, and inside a Cloud Run job (`CLOUD_RUN_JOB` set) inside its compute session (`compute.tracked_evaluation`: process `training:<project>`, resource `cloud_run`, its GPU passed to the session for simpl_tracker to price), whose recording never fails the evaluation.
    - **The scheduled sync.** `sync_pending(database, max_runs=, max_seconds=)` takes the runs not ended whose `environment.launch.files_only` is true (`RunRepository.pending_files_only`, random order, up to the cap) and, for each until the time cap, asks whether its Batch job or Cloud Run execution has ended (`sweep.launch.job_ended`, once for each job), applies its stored logs (`sync_stored_run`) and, when the job had ended and the run is still open, ends it failed or canceled with `JobEnded`. A run it cannot read is in `PendingPass.failed` and the others go on; `sync --pending` exits 1 naming them. Every write is replay-safe, so it is safe beside `sync --follow` and run twice. The image's entrypoint runs it, with no checkout and under the evaluator's token, when the job has `SIMPL_TRAINING_SYNC_PENDING`; the README has the `gcloud` setup of the scheduled job, its account and the scheduler.
  - **The courier:** `python -m simpl_foundry courier --from <directory> --to <artifact root> --run <id> [--run <id> ...] [--every SECONDS] [--max-hours 24]` (`courier.Courier`, `run_courier`) copies what is new of the runs' `logs/` and `artifacts/` from a store directory to their artifact root, under the same keys: each attempt's marker and log pieces in attempt and piece order, a piece only after every one before it (a single `events.jsonl`, which grows, is left to `collect`), and each artifact once its manifest is there and every file matches it, the manifest last, so an artifact in the destination is always complete; a run's pieces are listed before its artifacts are copied, so a piece recording an artifact stored arrives after it. It only creates objects (`put_file_if_absent`): what the destination holds is left, and it never reads, lists or deletes there, so a key that may only create objects is enough. One pass, or with `--every` a pass every SECONDS until SIGTERM or Ctrl-C (the pass under way is finished) or the cap. It reads no database setting and applies nothing; a run whose copy fails is named, exit 1, and the next pass tries again.
  - **The dependencies image:** `python -m simpl_foundry image build <recipe> [--dry-run]` (`job_image.build.build_dependencies_image`) builds and pushes the image remote jobs start from, to the recipe's `resources.image`, or for a recipe without a resources section to `SIMPL_TRAINING_REGISTRY/<repository>` (refused, naming the variable, when it is unset), tagged `lock-<first 16 hex of sha256(poetry.lock)>`: the locked packages of the repository holding the recipe, git ones at their locked commits, and this package's job entrypoint. A training repository keeps no image files: the context is this package's `Dockerfile` with the repository's `pyproject.toml` and `poetry.lock`. It must depend on `simpl-foundry[gcp]`, have an `origin` remote and, for jobs that use the database, a Secret Manager secret `<REPO>_DOPPLER_TOKEN` (the remote's last part in capitals, `-` as `_`). Run it after every lock change; it needs Docker with the registry's credentials and a `gh` login, whose token is a build secret and not in the pushed image.
  - **Choosing where a run trains** (`simpl_foundry.targets`, with the facts in `simpl_foundry.platforms` and the settings in `simpl_foundry.project_settings`): a recipe's `compute` section says where its job runs and on what, the same way on every target: `platform` (`local`, `batch`, `cloud_run` or `leonardo`), `gpus`, `cpus`, `memory_gb` and `hours`, and what one platform alone chooses: `nodes` and `queue` on Leonardo, `provisioning` (`spot` or `standard`), `fallback` and `boot_disk_gb` on Batch. `launch` and `sweep run` take `--on local|batch|cloud_run|leonardo` (`--target` is another spelling of it; giving both is refused) and `--gpus`, `--cpus`, `--memory-gb` and `--hours` (and `--nodes`, `--queue`), each replacing its field; with no `--on` the recipe's `compute.platform` says, else `local`. On a target other than the section's `platform`, a field the recipe set carries over only when that platform takes it (`takes` in its facts: `platforms.BATCH`, `platforms.CLOUD_RUN`, `leonardo.cluster.LEONARDO`); the others are left out (`Destination.left_out`) and the launcher prints them, `compute: left out cpus, memory_gb, which leonardo does not take; ...` (`targets.left_out_line`). So `compute: {platform: cloud_run, gpus: 1, cpus: 8, memory_gb: 32, hours: 2}` keeps its vCPUs and memory on Batch and launches `--on leonardo` with Leonardo's 8 CPUs for its GPU. A command-line option, and every field on the section's own platform, is checked as given. `targets.destination` resolves it when the launch is planned and refuses, every problem named in one error, before anything is queued, built or pushed:
    - `local`: needs nothing; a sizing option is refused.
    - `batch`: the smallest G2 machine (fewest GPUs, then fewest vCPUs) giving at least `gpus` (1 by default), `cpus` and `memory_gb`, with all its L4s (24 GB each): `g2-standard-4` 1 GPU, 4 vCPUs, 16 GB; `-8` 1, 8, 32; `-12` 1, 12, 48; `-16` 1, 16, 64; `-24` 2, 24, 96; `-32` 1, 32, 128; `-48` 4, 48, 192; `-96` 8, 96, 384. A request no machine gives is refused naming the two closest. `hours` is required, up to 168. Spot, `fallback: standard` and a 100 GB boot disk unless the section says otherwise; `queue` and more than one node are refused.
    - `cloud_run`: one L4, `cpus` 4 to 8 and `memory_gb` 16 to 32 (8 and 32 when unset), `hours` required, up to 12; more GPUs, `queue`, `provisioning`, `fallback` and `boot_disk_gb` are refused.
    - `leonardo`: the Slurm allocation, see *On Leonardo*.

    On Batch and Cloud Run the section becomes the `RecipeResources` the job runs on, with what belongs to the Google Cloud project rather than to a model taken from the environment: the image `SIMPL_TRAINING_REGISTRY/<repository>` (the last part of the trainer's repository's `origin`, as `image build` names it), `SIMPL_TRAINING_SERVICE_ACCOUNT` (for a files-only job `SIMPL_TRAINING_FILES_ONLY_ACCOUNT`, and the network settings) and `SIMPL_TRAINING_REGION`. A recipe with no `tracking.artifact_root` takes `SIMPL_TRAINING_ARTIFACT_ROOT` (a `gs://` location) when it is run, launched or swept, on any target (`recipe.project_placement`). None has a default, and a launch that needs an unset one is refused naming it; so a recipe names no image, account, region or bucket. A recipe's own `resources` section wins on Batch and Cloud Run: it needs none of these settings, a sizing option is refused and its compute section is not read there, and on Cloud Run it is held to the same limits (`cloud_run.check_limits`). What the launch resolved goes into the recipe the run records (`plan_experiment(..., placement=)` and `plan_sweep(..., placement=)` with a `recipe.Placement`: `ExperimentPlan.resolved`, a sweep's stored recipe), so a job reads its resources from its queued config and needs no setting, and a run queued with a `resources` section runs as before. `runs.recipe_hash` stays the hash of the recipe as declared. The platforms' facts are data in `platforms.BATCH` and `platforms.CLOUD_RUN`; `simpl_core`'s agent tools resolve a recipe through `targets.destination` too, so a recipe they launch needs only its compute section.
  - **On Google Batch:** the resources, resolved from the compute section or a recipe's own `resources` section, say where a Batch job runs: `image` (the training repository's GPU image in Artifact Registry, `<region>-docker.pkg.dev/<project>/<repository>/<image>` without a tag; project and region come from it), `machine` (`g2-standard-8`), `gpu` (`nvidia-l4`) and `gpu_count`, `provisioning` (`spot` or `standard`), `fallback` (`standard` or `none`), `max_hours` (6: a job gets that long from when its run started, across its attempts, and a run past it fails), `boot_disk_gb`, `region`, `service_account` (`training-runner` in the image's project, or a full email), and `network` with `subnetwork` (none by default; see *Files-only on Google Cloud*; a recipe with its own `resources` section gets a new `recipe_hash`, as the dump now holds them). `simpl_foundry launch <recipe> --on batch` needs them and a `gs://` artifact root; it queues the run, then `launch_batch` builds the job's image on this machine (`code_image`: `FROM <image>:lock-<first 16 hex of sha256(poetry.lock)>`, the training repository's dependencies image for the launching checkout's lock file, `image_tag`, plus the commit's files from `git archive` at `/job/checkout`; tagged `code-<first 12 hex of the commit>-<the lock's 16 hex>` (`code_images`), built for `linux/amd64` with `docker buildx` and pushed, so it needs Docker and the registry's credentials here; a tag already in the registry is reused, so a commit relaunched keeps its base, and it builds only when the registry says the tag is missing: any other `imagetools inspect` failure fails the launch), and submits one task in it, with `SIMPL_TRAINING_RUN_ID`, `SIMPL_CODE_COMMIT` and `SIMPL_CODE_REPO`, labels `simpl_repo` and `training_run_id` on the job and its VMs, `maxRetryCount` 3 a task with a GPU mounting `/var/lib/nvidia` and running `--privileged` with the driver's libraries on `LD_LIBRARY_PATH` (`installGpuDrivers` alone leaves the container on the CPU), and one lifecycle policy, the most Batch accepts: `FAIL_TASK` on exit 1 and 2, so every other failure (a preempted VM's 50001, a stopped job's 143) is retried. A launch that raises, Ctrl-C included, ends its run as canceled with the error (type `LaunchFailed`), and a run canceled while its image builds gets no job (`launch_batch` returns `None`). The job is recorded in the run's environment under `batch` before it is submitted (job, image, provisioning, Cloud Console link, submission time, `previous` jobs with the reason each was replaced). `--wait`, the default, follows it (`watch_job`) until a task runs, and replaces a Spot job refused for capacity, or still waiting after 15 minutes, once by a standard one when `fallback: standard`, a replacement that cannot be submitted ending the run as a launch does; with `--no-wait` nothing watches it, so a Spot job waits with no fallback; `--dry-run` prints the job spec and writes nothing. `simpl_foundry cancel <run id>` (`cancel_run`) ends a queued or Batch run as canceled, then deletes its job, and on a canceled run deletes the job again; a running local run is stopped from its process. `simpl_foundry resume <run id> [--wait]` (`resume_run`) submits the same image, commit and provisioning again for a run that is queued or left running, and is refused while its last job may still run a task. The Batch API is called over `httpx` with Application Default Credentials (`google-auth`, from the `gcp` extra). A remote job whose recipe asks for a GPU and that sees none ends its run (`NoGpu`: canceled when queued, else failed) and exits 2 rather than train on the CPU; a retry of it exits 1. A job on Batch runs inside a simpl_tracker compute session (`tracked_compute`: process `training:<project>`, resource `compute_engine`, service type `job` or `spot_job` by its provisioning, the machine's CPU and memory, its region), loading this package's `job_image/tracker.yaml`; a configuration that cannot be loaded, or a resource `cost_tracking.infra_resource` does not have, is reported as `compute_tracking.missing`. The job's GPUs (`gpu_count` x `gpu`, also on Cloud Run) go to the session, which simpl_tracker (0.8.26 on) prices per GPU-second and reports as `compute_tracking.gpu_unpriced` when it has no rate for the GPU type; on Batch it also records the VM's name as Google's bill gives it, so on billed days the VM's cost goes to the session's repo and process. A training repository whose lock holds an older simpl_tracker gets no GPU in the session, and the job reports its GPU time as `compute_tracking.gpu_unpriced` itself: relock it. None of this ever fails or delays the job.
  - **As a Cloud Run job:** `simpl_foundry launch <recipe> --on cloud_run` (`cloud_run.launch_cloud_run`) builds and pushes the same code image, then creates the Cloud Run job `train-<first 12 hex of the run id>` in the recipe's region (`resources.region`, else the image's) with one task: `cpu` (default 8) and `memory_gb` (default 32) of the recipe's `resources`, one `gpu` (`nodeSelector` accelerator, no GPU zonal redundancy), a timeout of `max_hours`, `maxRetries` 3, the recipe's `service_account`, labels `simpl_repo` and `training_run_id`, launch stage `BETA` (GPU tasks over an hour are a preview feature); and starts one execution. `check_limits` refuses, before anything is queued, what a Cloud Run task cannot have (`platforms.CLOUD_RUN`): a GPU other than `nvidia-l4` or `nvidia-rtx-pro-6000`, more than one, CPUs outside 4 to 8, memory outside 16 to 32 GB, over 12 hours. There is no Spot: tasks run on demand, and Cloud Run retries a failed task whatever its exit code (a retry of an ended run exits at once, with code 1 for a failed run or one canceled for `NoGpu`). The job is recorded in the run's environment under `cloud_run` (job, execution, image, Cloud Console link, start time, `previous` executions), its name before it is created, so `simpl_foundry cancel` can delete a job whose creation timed out. `--wait` follows the execution (`watch_execution`) until its task runs or it fails, printing the failed condition; `--dry-run` prints the job. `simpl_foundry cancel` ends the run, cancels its execution and deletes the job (`stop_job`); `simpl_foundry resume` starts a new execution of the job (`resume_execution`). A launch that raises, Ctrl-C included, ends its run as canceled (`LaunchFailed`) and deletes a job it knows it created; a run canceled while its image builds gets no job (`launch_cloud_run` returns `None`). On Cloud Run the job's compute session is simpl_tracker's resource `cloud_run`, sized by simpl_tracker (the task has `CLOUD_RUN_JOB`). The target needs the migration that adds `cloud_run` to `training.launch_target`.
  - **On Leonardo** (`simpl_foundry.leonardo`): the CINECA HPC system, from your machine over your own SSH login. Settings, read from the environment with no default: `SIMPL_LEONARDO_HOST` (an alias of your SSH config), `SIMPL_LEONARDO_ACCOUNT` (the Slurm account) and `SIMPL_LEONARDO_DIR` (an absolute directory under `$WORK` that simpl_foundry owns); a missing one is an error naming it. `ssh` and `rsync` run as subprocesses with `BatchMode=yes`; simpl_foundry never handles a key. A GPU node reaches no internet, so the job is the files-only job and everything it reads is staged first.
    - **Compute.** A recipe's `compute` section (`platform: leonardo`, `gpus`, `nodes`, `hours`, `queue`; `on` is a YAML boolean, hence `platform`) and the options `--on leonardo --gpus N --nodes N --hours H --queue Q` of `launch` and `sweep run`, which replace its fields (`--cpus` and `--memory-gb` too). `leonardo.allocate` turns it into the Slurm request: partition `boost_usr_prod`, one node, `--gres=gpu:N` with N from 1 to 4 and 8 CPUs for each GPU (no `--mem`: the default memory for each CPU gives a GPU's share), `--time` from `hours`, which is required. The queue follows `hours` (normal up to 24, `boost_qos_lprod` up to 96), and `--queue debug` asks for `boost_qos_dbg`, up to 0.5. More GPUs, more than one node (one run on several nodes needs distributed training, which simpl_foundry does not do), more hours, `cpus`, `memory_gb` and Batch's `provisioning`, `fallback` and `boot_disk_gb` are refused, every problem named, before anything is queued or staged; a section written for another platform has the last five left out instead. Leonardo's facts are data in `leonardo.cluster.LEONARDO`.
    - **Image.** `simpl_foundry image build <recipe> --on leonardo` makes the dependencies image `image build` pushed (`lock-<hash>` of the recipe's `resources.image`) a Singularity image there: `docker pull` and `docker save` here, the archive copied there, and a job on the serial queue (`lrd_all_serial`) builds `images/<repo>-lock-<hash>.sif` and removes the archive. An image there for the same lock is reused. No registry credential is sent. The job's code is not in the image, and the training repository's lock must pin a simpl_foundry that has `job --mirror`.
    - **Launch.** `launch <recipe> --on leonardo` checks that the checkout's image is there, that the recipe has an artifact root and that its `base_model` is not a local directory, queues the run (`launch_target` `leonardo`), then `leonardo.launch_run` stages it under `SIMPL_LEONARDO_DIR`: the run's store view (`runs/<id>/store`: its `spec.json`, empty `logs/<id>` and `artifacts/<id>`), the snapshot's trainer part (`datasets/<fingerprint>`) and the commit's files (`code/<commit>`, from `git archive`), each reused when there. Held-out rows never go there: `staging.check_staged` refuses, before anything is sent, a file outside those places, a snapshot directory holding a held-out role or a file its `snapshot.json` does not list, and a commit file whose content is one of the snapshot's source files. The base model, at the commit its experiment resolved, and `hub_repositories`, at `main`, are downloaded on a login node, inside the image, into the `hf` cache there. The `sbatch` script runs `simpl_foundry job <id> --store /store --mirror --require-gpu` (a job that sees no GPU exits 2 before it claims an attempt, so it never trains on the CPU) under `singularity exec --nv --containall --no-home`, with binds for exactly the run's `runs/<id>`, `logs/<id>` and `artifacts/<id>` (read-write), its snapshot, the commit and the Hub cache (read-only) and its work directory (read-write), `HF_HUB_OFFLINE=1`, and every variable named. Slurm signals the script 10 minutes (a tenth of a shorter limit) before `--time`; the job closes its run and exits 143, and the script requeues it, at most 3 times (`MAX_REQUEUES`; exit 75 too), so the next attempt resumes from the last stored checkpoint. The run's environment records `leonardo`: the job's id, account, queue, QOS, GPUs, CPUs, hours, script, image and when it was submitted. A launch that raises ends the run as canceled (`LaunchFailed`).
    - **Sweeps.** `sweep run <recipe> ... --on leonardo` submits one job array, a task for each trial to train, `--parallel` at a time; a task finds its run in `sweeps/<sweep id>/tasks.tsv` by `SLURM_ARRAY_TASK_ID`, with no database. `--max-gpu-hours` counts each trial's requeues.
    - **Courier.** With `SIMPL_LEONARDO_GCS_KEY` set to the absolute path, on Leonardo, of a Google Cloud service account key that may only create objects in the artifact bucket (`roles/storage.objectCreator` on that bucket, nothing else; keep it mode 600 under your `$HOME` there), `launch --on leonardo` and `sweep run --on leonardo` also submit a courier job on the serial queue (`lrd_all_serial`, which reaches the internet; one for a run, one for a sweep's array). It runs `simpl_foundry courier` in the same image with `--containall --no-home`, binding only the runs' `logs/<id>` and `artifacts/<id>` (read-only) and the key (at `/credentials/gcs-key.json`, `GOOGLE_APPLICATION_CREDENTIALS`), a pass every 60 s while the training job is in the queue (`squeue`), then a last pass once it has left. Before the serial queue's 4 h limit it ends its round and, while the training job is still queued or running, resubmits itself (`sbatch <script> <training job> <round>`), at most `ceil(tasks one after the other × hours × 4 attempts / round) + 2` rounds (`script.courier_timing`). simpl_foundry only names the key's path in the script: it never reads or sends the key, and `launch` refuses a path Leonardo does not have. A courier that cannot be submitted is logged and the training goes on. The run's environment records the courier's Slurm id as `leonardo.courier`. Without the setting no courier runs and the launcher says so: `collect` brings the files back. The image's simpl_foundry must have the `courier` command and log pieces.
    - **Collect.** `simpl_foundry collect <run id>` (`leonardo.collect_run`), or `collect --sweep <id>`, on your machine: copies the run's `logs/` and `artifacts/` from Leonardo (regular files only), creates in the run's artifact root, under the same keys, what it lacks (attempt markers, log pieces, an artifact once complete and checked against its manifest, manifest last: the courier's copy, `courier.Courier`) and uploads a single `events.jsonl` every time, deletes there the checkpoints its logs record as deleted, then applies the logs (`sync_stored_run`). Safe to repeat, to run while the job runs and beside a courier; nothing is sent to Leonardo.
    - **Collect while it trains.** `simpl_foundry collect <run id> --follow [--interval 60] [--max-hours 24]` (`leonardo.collect.follow_run`) is the way to see epochs as a job trains with no courier and no key on Leonardo: each pass copies only the run's logs and applies them; the artifacts are copied once, in the pass whose logs end the run, before that end is applied. It needs this machine on and a valid login for as long as it follows; an expired login stops it at once, and a plain `collect` finishes the job later. Until the run ends a checkpoint's row names a file the artifact root does not hold yet. Not for `--sweep`.
    - **Cancel and resume** (`simpl_foundry.leonardo.control`, through `cancel_run`, `resume_run` and `cancel_sweep`, which take the login as `leonardo=`, by default `Remote(LeonardoSettings.from_environment().host)`). A run records what they need when it is submitted: under `leonardo`, its directory there, its script, its Slurm job's id and its courier's, and for a sweep's run its task of the array (`array_task`); a Leonardo sweep's `launch_ref` names the array, its courier and the directory. `simpl_foundry cancel <run id>` first writes the run's stop marker (`runs/<id>/canceled` there, which the container does not see), then `scancel`s its job and its courier, or for a sweep's trial its own task (`<job>_<task>`) and nothing else, each only while `squeue` lists it, and only then ends the run as canceled and records `leonardo.canceled_at` and `canceled_jobs`; a second cancel does nothing. `sweep cancel <id>` does the same for the open runs of the sweep's array, the array and its courier. The job script checks the stop marker before it starts the job and before it requeues it, since `scancel`'s SIGTERM would otherwise end in the same requeue as a time limit. `simpl_foundry resume <run id>` submits the run's script again, and its courier when it had one, recording the job it replaces under `leonardo.previous`; a Leonardo run's row stays `queued` until its first log is applied, so resume asks `squeue` whether the last job may still run (pending, running or completing; a job Slurm no longer knows may not) and refuses while it does. A sweep's trial is refused, as on Batch. Without a login (ssh fails in batch mode, exit 255) each raises `leonardo.NoLogin`, a `RemoteError`, before any row changes; the commands exit 1 and say so.
    - The target needs the migration `src/simpl_foundry/migrations/20261105_training_launch_target_leonardo.sql`.
  - **Sweeps** (`simpl_foundry.sweep`, `src/simpl_foundry/migrations/20261104_training_sweeps.sql`): `simpl_foundry sweep run <recipe> --grid training.learning_rate=1e-6,5e-6 --grid training.num_train_epochs=2,3 --seeds 3 --parallel 4 --max-gpu-hours 8 --on batch --gpus 1 --hours 2` (or `--random N [--vary KEY]`; `--on local` runs the trials one after the other, `cloud_run` as one job too, `leonardo` as a job array; the compute section and its options size the job as for `launch`; `--dry-run` prints the plan). `plan_sweep` checks every point against `search_surface` and plans it; points that make the same experiment count once, and a point a run has finished, is running with a live heartbeat, or holds queued with a recorded job for less than `existing.QUEUED_COVERS_FOR`, at the same seed trains nothing and that run joins the ranking. `check_budget` refuses a sweep whose trials × `max_hours` exceed `--max-gpu-hours`. `queue_sweep` first calls the evaluator module's `check_recipe(recipe)`, if it defines one, then writes `training.sweeps`, a queued run per trial (`group_name` `sweep-<id>`, `runs.sweep_id`, `runs.trial_id`) and `training.trials` (`task_index` null for a reused run); `queue_sweep(created_by=)` (and `queue_run(created_by=)`) names who submits it, such as `campaign:<id>`, recorded as `created_by` on the sweep, on each run it queues and on an experiment or snapshot record it creates, and read back as `read_sweep(...).created_by`; without it, the checkout's git `user.email`; `launch_sweep` submits one job with a task per trial. A task runs `simpl_foundry job --sweep <id>`, which finds its run by `BATCH_TASK_INDEX` or `CLOUD_RUN_TASK_INDEX` (`run_of_task`): the job's image reads `SIMPL_TRAINING_SWEEP_ID`. From there a trial is an ordinary run, except that `simpl_foundry resume` refuses it and `simpl_foundry cancel` ends the run and keeps the job (on Leonardo it cancels the trial's task of the array): `simpl_foundry sweep cancel <id>` ends the runs of the sweep's job and deletes it. A recipe needs `evaluator` (`"package.module:function"`, `evaluate(model_dir, data: EvaluationData) -> Mapping[str, float]`, `data` holding `split`, `rows`, `assets`, `hyperparameters` and the recipe's `base_model`; it raises `ValueError` for a model it can never score; its module may define `EVALUATOR_CODE`, `evaluator_settings(data)` and `check_recipe(recipe)`, which raises `ValueError` for a recipe it can never score, so that recipe is refused before any GPU is spent), `objective` (`metric: <split>/<metric>` on a held-out role, `goal`, `noise_band`, `simpler`: hyperparameters whose lower value is simpler) and optionally `acceptance_rule` (`metric`, `goal`: which way it is better, the objective's when unset, `against`: the run whose model serves today). `simpl_foundry sweep evaluate <id>` (`evaluate_sweep`) scores each finished trial's `final` model on the objective's split, reusing a score already recorded the same way, and ends the sweep once no trial waits. While the sweep is open, a trial scored another way is evaluated again, so the sweep ranks under the latest way of judging. A run with no `final` model, a `ValueError` from the evaluator, a non-finite metric or a missing objective metric fails the trial for good (`Unscorable`); a model that fails its manifest (a changed file, a path outside the artifact) fails it too; any other error, a connection's or a disk's, leaves the trial waiting for the next evaluate and is printed. `sweep evaluate <id> --fail-unscored` is the way out when that error will not pass: it fails those trials and those waiting for another's run, so the sweep finishes with the scores it has and `sweep promote --accept-failed` can use them, where `sweep cancel` would lose them. Once the sweep's job has ended, it also ends the runs the job left open (`JobEnded`: failed, or canceled if never started). It reads the snapshot's held-out part where `training.datasets.hidden_uri` says it went (the held-out root, or the artifact root's `hidden/`), so it runs under an account allowed to: `--on cloud_run` runs it as the evaluator's own job (see *Held-out rows, the evaluation job and the scheduled sync*). `rank_trials` takes the mean over seeds; means within `noise_band` tie and the simplest wins. Trials that failed, were canceled or hold a non-finite score are left out and named (`Ranking.unranked`, in `sweep show` and the report). `simpl_foundry sweep promote <id> [--recipe FILE] [--out DIR] [--accept-failed]` (`promote_sweep`) refuses a sweep with an unranked trial unless `--accept-failed` is given, as the best point may be among them, then checks the acceptance rule, writes `<recipe file>.patch`, for `git apply` at the root of the recipe's repository, and a report, and marks trials `promoted` and `rejected`; a winner worse than the serving model gets the report and no patch, and so does a winner whose values the recipe already holds, its trials still settled. It activates nothing. `simpl_foundry sweep show <id>` prints where a sweep stands.
  - **The sealed test set.** Give the recipe two held-out roles, rank on one and accept on the other: `objective: {metric: select/f1}` and `acceptance_rule: {metric: acceptance/f1}`, with a split such as `roles: {train: train, dev: dev, select: test, acceptance: gold}`. A sweep's evaluation, its ranking, `read_sweep`, `sweep show` and the scores it stores (`training.trials.score`, its `training.evaluations` rows) only ever score or show the objective's split; only `sweep promote` scores the acceptance rule's, once for the winner's best seed and for the serving run. `Recipe.sealed_split` says which split that is: the acceptance rule's when it differs from the objective's, else `None`, so a caller driving rounds of sweeps can require one. The evaluation still downloads the snapshot's whole held-out part, both roles, where it runs.
  - **Held-out reads.** Each round that shows a held-out score lets whoever chooses the next round fit those rows a little. `EvaluationRepository.experiments_scored(recipe_name, split=, since=)` counts the distinct experiments of a recipe scored on one split (good evaluations recorded at or after `since`, whatever evaluator judged them, an experiment scored again counted once), so a caller can stop submitting past a cap across all its campaigns. It is a query: nothing here enforces a cap.
  - **Agents:** the recipe declares what an agent may do: `search_surface`, `code_surface` (patterns relative to the trainer's package; empty means no patch) and `budget: {max_gpu_hours: N}` per agent run (none means no submit). The `experiment_*` tools that read them are `simpl_core`'s, since they need its agent framework. What they use here: `queue_sweep(created_by=)` to mark a campaign's sweeps, `Recipe.sealed_split` and `EvaluationRepository.experiments_scored` (see *The sealed test set* and *Held-out reads*).
  - **Planning:** `plan_experiment(recipe, overrides=, seed=, look_up=True, database=)` checks the overrides, reads the sources, hashes the code, the data and the base model into the experiment, and reads its runs and `training.evaluation_scores` (`ExperimentPlan.existing`, `covering_runs()`), building no snapshot and writing nothing; `run_plan(plan, ...)` runs it. `find_experiment(settings, hash)` and `render_existing` are the lookup and its text. The run is written under `runs/<recipe>` by default, records the recipe's name on its experiment, the recipe's hash as declared in `runs.recipe_hash`, the overrides in `runs.overrides`, the resolved recipe as its config, the snapshot in `training.run_datasets`, and the snapshot and rows per role in its environment (`data.snapshot`, `data.roles`, `data.unassigned`). The CLI prints whether the snapshot was built or reused.
  - **Snapshots** (`simpl_foundry.snapshot`, `training.datasets`): the data as rows by role, written once per fingerprint (the split, the kept columns and the content of every source and asset file, a table read included; paths, file and table names do not count). The roles a trainer receives and the assets go under `datasets/<fingerprint>/` of the recipe's `artifact_root`, the held-out roles under `hidden/datasets/<fingerprint>/` of the held-out root when `SIMPL_TRAINING_HELD_OUT_ROOT` is set, else of the artifact root (deny that prefix to trainers), each an artifact with a `manifest.json` and a `snapshot.json`; without an artifact root only the local copy exists. `training.datasets.hidden_uri` records where the held-out part went. A run looks in the local cache (`snapshot_cache_dir()`: `SIMPL_TRAINING_CACHE`, else `$XDG_CACHE_HOME/simpl_foundry`, else `~/.cache/simpl_foundry`), then the store, and builds only when neither has it; a cached snapshot the store lacks is uploaded. Rows come back exactly: list, mapping and mixed-type columns are stored as JSON text and decoded on read; a role whose rows lack a column others have is refused (keep a fixed set with `data.columns`). A build refuses a source or asset file that changed after the fingerprint was taken, a split that gives `train` no rows, and a `data.columns` entry the first row lacks. A trainer part's `snapshot.json` gives each source's `kind`, `sha256` and `size` only and leaves `source` out of its `declaration`; the full records stay in `training.datasets`.
  - **The trainer** is `fit(data: TrainingData, params: TrainerParams, run: Run)`: `data.train`, `data.dev` (row dicts read from the snapshot), `data.assets` (the snapshot's copies, by name), `data.role_counts`, `data.snapshot` (`DatasetSnapshot`: `rows(role)`, `to_arrow(role)`, `to_hf(role)` with JSON columns as text); `params.base_model`, `params.hyperparameters` (overrides applied), `params.seed`. It writes under `run.directory`. Raising fails the run and propagates. Its module may define `IDENTITY_EXCLUDE`, dotted paths inside `hyperparameters` that do not change the trained model.
  - **Identity** (version 2, `snapshot_experiment_identity`): the trainer entry point and the hyperparameters minus `IDENTITY_EXCLUDE` as config, the trainer's top-level package as code, the snapshot's fingerprint as data, and the base model. The recipe's name, seed and tracking section are left out, so seed replicates share an experiment.
- **`python -m simpl_foundry diff <experiment> <experiment>`** takes hashes or unique prefixes and prints the config keys, code files, data files and base weights that differ, with the GitHub link comparing the two code commits (`simpl_foundry.diff`).
- Migration `src/simpl_foundry/migrations/20261102_training_evaluations.sql` (after the two above): `runs.metric_goals`, `training.evaluations`, the `evaluation_scores` view and the `metric_series` function.
- **Repositories** (`simpl_foundry.repositories`): `ExperimentRepository` (`find_or_create`, `set_code_commit`), `DatasetRepository` (`find_or_create`, a local location replaced by a later `gs://` one; `link_run`), `RunRepository` (`create`, `heartbeat` (forward-only), `merge_environment`, `resume`, `resume_state`, `end` with the state guard, `IllegalRunTransition`), `MetricRepository.upsert`, `EvaluationRepository` (`record`, `scores_of_run`, `leaderboard`, `experiments_scored`), and `ArtifactRepository` (`create`, `mark_stored`, `mark_failed`, `mark_deleted`, `set_alias`, `aliases`). Every write is replay-safe.

## A model repository's trainer, outside a recipe

A model repository keeps only what is its own: its code root, which config keys name data files, which keys stay out of an experiment, and how its models are judged. The rest is here.

- **`Tracking`** (`simpl_foundry.Tracking`): a config's `tracking` section, a frozen dataclass: `project`, `tags` (a tuple), `offline` (events on disk only, for `sync`) and `artifact_root` (`gs://bucket/prefix` or a directory; `None` stores no checkpoint or model). `Tracking.from_mapping(raw)` reads it from a YAML mapping; no `project` is a `KeyError`. A config without the section records nothing. A recipe's own section is `RecipeTracking`, without `offline` (a run's `--offline`).
- **Hugging Face** (`simpl_foundry.integrations.hf`, the `hf` extra):
  - `tracked_run(tracking, config=, training_key=, run_dir=, code_root=, data_files=, base_model=, config_exclude=(), resume=None)` is a context manager giving the run, or `None` when `tracking` is `None` (`resume` then raises `ValueError`). The experiment is `config` without `config_exclude`, without the keys `data_files` names (a role to the dotted key of a file's path in `config`: the file enters by content) and without `HF_NON_IDENTITY_ARGS` and `HF_SEED_ARGS` (`seed`, `data_seed`) under `training_key`, the trainer's arguments; plus the code under `code_root` and `base_model`. The run's seed is the arguments' `seed`, so replicates differing only by seed share an experiment. Leaving the block finishes the run, an exception fails it.
  - `tracking_callbacks(run)`: `[SimplCallback(run)]`, or `[]` without a run.
  - `resume_checkpoint(run, checkpoints_dir, download_dir=, load_best=, required=True)`: the checkpoint a resumed run (its next attempt) continues from, in the trainer's `output_dir`: the stored `latest`, downloaded into `download_dir`, checked and moved there as `checkpoint-<step>` (replacing a folder of that name, so the trainer's rotation removes it like its own), else the run's own newest checkpoint on disk (`latest_run_checkpoint`). With `load_best` the stored `best` goes back too, unless the trainer state of `latest` names it as best. No checkpoint raises `LookupError`, or gives `None` with `required=False` (a job retried before its first checkpoint starts over).
- **Lightning** (`simpl_foundry.integrations.lightning_cli`, the `lightning` extra): `TrackedCLI(model, datamodule, code_root=, runs=ExitStack(), data_files={"records": "data.records"}, identity_exclude=("data.num_workers",), args=...)` is a LightningCLI with a `--tracking` argument (`Tracking`). Its `fit` with a section opens the run (`tracked_fit`) in `trainer.default_root_dir`, records the device, and appends `SimplLogger`; the run ends with `runs`: finished when the command returns, failed when it raises. A tracked fit without `runs` raises `RuntimeError`. The experiment leaves out `CLI_NON_IDENTITY_KEYS` (`config`, `ckpt_path`, `seed_everything`, `tracking`), the `data_files` keys, `identity_exclude` and `trainer.` `LIGHTNING_NON_IDENTITY_ARGS`; the model starts from scratch, and the run's seed is an integer `seed_everything`. A subclass that links arguments calls `super().add_arguments_to_parser`.
- **The run's model and report** (`simpl_foundry.tracking`): `store_model(run, model_dir)` stores the saved model as the run's `final` (nothing without a run or an artifact root). A trainer's JSON report names its run under `REPORT_KEY` (`"tracking"`) as `run_reference(run)` gives it (`run_id`, `experiment_hash`, `attempt`); `run_of_report(path)` reads the id back (`None` without the file or the key), so an evaluation later logs its scores on the run that trained the model (`log_evaluation`).
- The code hash covers the whole `code_root`, so moving a file out of a model repository's package changes its experiments.

```python
from simpl_foundry import Tracking
from simpl_foundry.integrations.hf import tracked_run, tracking_callbacks
from simpl_foundry.tracking import REPORT_KEY, run_reference, store_model

tracking = Tracking.from_mapping(raw["tracking"]) if raw.get("tracking") else None
with tracked_run(tracking, config=raw, training_key="training", run_dir=output_dir,
                 code_root=CODE_ROOT, data_files={"records": "records"},
                 base_model=raw["checkpoint"], config_exclude=["output_dir", "tracking"]) as run:
    trainer = Trainer(..., callbacks=tracking_callbacks(run))
    trainer.train()
    trainer.save_model(str(output_dir / "model"))
    if run is not None:
        report[REPORT_KEY] = run_reference(run)
    store_model(run, output_dir / "model")
```

## Adding a source reader

A reader adds a kind of recipe source. Declare it as an entry point named by its kind; the value is a callable taking a `ReaderContext` and returning the reader. Its module is imported only when a recipe uses that kind.

```toml
[project.entry-points."simpl_foundry.sources"]
row_store = "simpl_core.row_store.source_reader:RowStoreReader"
```

```python
from collections.abc import Mapping
from pathlib import Path
from typing import Any

from pydantic import BaseModel
from simpl_foundry import ReaderContext, SourceRead, WhereClause
from simpl_foundry.sources import check_columns, run_blocking, write_read


class ExampleSource(BaseModel):
    example: str                    # a field named as the kind
    columns: list[str]
    where: list[WhereClause] = []


class ExampleReader:
    kind = "example"

    def __init__(self, context: ReaderContext) -> None:
        self._database = context.database

    def parse(self, spec: Mapping[str, Any]) -> ExampleSource:
        return ExampleSource.model_validate(spec)

    def read(self, spec: ExampleSource, cache_dir: Path) -> list[SourceRead]:
        rows = run_blocking(read_rows_somewhere(spec))
        read = write_read(
            rows,
            columns=spec.columns,
            where=spec.where,
            cache_dir=cache_dir,
            metadata={"kind": "example", "dataset": spec.example},
            label=f"example:{spec.example}",
        )
        return [read]
```

- `parse` returns a model with a field named as the kind, which dumps back to the same mapping: a recipe's hash is taken from that dump.
- `read` returns one `SourceRead` per file, in order: `path`, `sha256`, `metadata` and `label`. `metadata` must hold `kind` and `size`. `write_read` adds `size`, the columns, the clauses and the row count to rows it writes.
- A snapshot's fingerprint covers each read's `kind` and `sha256`, so keep what moves without the rows changing, such as a store's version, out of the file.
- `label` is what the run's `data.sources` lists.
- `check_columns(columns, where, available, name)` raises the `ValueError` naming what a source lacks.

## Rules and conventions

STRICT (enforced in review):

- A trainer receives only `train` and `dev` rows. Give anything a trainer runs as no right on the held-out root, and deny it the `hidden/` prefix of the artifact root, where snapshots stored before the held-out root keep their held-out rows.
- A run's data is pinned when it is queued (`environment.launch.trainer_checksum`); never rewrite a stored trainer part.
- Promotion activates nothing. `sweep promote` writes a patch and a report; a person opens the pull request.
- Keep the schema `training`, `refs/training/*`, `SIMPL_TRAINING_*`, `SIMPL_CODE_*` and the `training.*` log events as they are: stored data and running jobs use them.
- Migrations are SQL files in `src/simpl_foundry/migrations/`, applied in name order by a person.

FLEXIBLE (defaults):

- `--if-exists replicate` runs another replicate of an experiment; use `skip` in scripts that may repeat.
- `--wait` follows a job until a task runs; use `--no-wait` only when nothing needs the Spot fallback.

## Common pitfalls

- **Don't** run `python -m simpl_core training job`: that command left with this package. An image's entrypoint runs `python -m simpl_foundry job`.
- **Don't** expect a `sweep promote` patch every time: on the first Cloud Run sweep the winner was the recipe's own value and the patch only rewrote `5.0e-6` as `5.0e-06`. Such a winner now gets no patch, and the report says so.
- **Don't** look for `training_run_id` on a sweep's job in the bill: that job carries `training_sweep_id`.
- **Don't** treat a job that uses the database as isolated: it holds everything its Doppler config holds. A files-only job on Google Cloud holds no secret and, with the network settings, reaches no internet; run code no person has reviewed only that way, and only once its account has exactly the rights the README lists. It can still create objects under other runs' `logs/` and `artifacts/` prefixes: a signed run's sync skips and reports them, an unsigned run's would read them.
- **Don't** put `SIMPL_TRAINING_LOG_SECRET` where a job runs: not in a job's variables, nor in the Doppler config a training repository's jobs read. Whoever holds it can sign any run's log. The evaluation job and the scheduled sync read it from their own token, `<REPO>_EVALUATOR_DOPPLER_TOKEN`.
- **Don't** expect `sweep promote` of a recipe with an acceptance rule to run where the held-out root cannot be read: it scores the winner on the held-out part.

## Testing

Tests that start a run in a real checkout with a `code_root` set `SIMPL_CODE_COMMIT` (any 40-hex value), or they push a ref to that checkout's remote. `offline=True` keeps a run off the database. A test binds a reader to its own store with `SourceRegistry.register`.

```python
from simpl_foundry import SourceRegistry, init_run


def test_a_run_logs_offline(tmp_path, identity):
    with init_run(project="example", identity=identity, config={}, run_dir=tmp_path, offline=True) as run:
        run.log({"train/loss": 0.5}, step=1)


def test_a_reader_bound_to_a_local_store(store):
    SourceRegistry.register("example", lambda context: ExampleReader(context), override=True)
```

## What this library does NOT do

- Does not call models or serve them: model calls go through `simpl_core`'s agent framework, and serving is elsewhere.
- Does not hold the `experiment_*` agent tools or the `row_store` reader: `simpl_core` does.
- Does not activate a model.
- Does not apply migrations.
